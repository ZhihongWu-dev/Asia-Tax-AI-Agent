2026-09-05 的记录证明当时的命令行切片已做过模型、数据库和候选案例集成验证；不证明当前 DeepSeek 配置可用，也不等于 FR-01 至 FR-08 全部交付。历史记录中的 RAG 是规则定位到法律单元的引用能力，不能据此认定已具备路线图要求的关键词与向量混合检索。

## 按技术路线推进的顺序

1. **先打通可交互的最小真实链路。** 在现有 Python 模块上新增案件/聊天/事实接口；接入当前 DeepSeek 配置并验证失败处理；保存会话；根据缺失信息多轮追问；顾问确认事实后再运行分析。用一个候选案例验证“输入 → 追问 → 确认 → 研究结果与来源”，并验证刷新恢复、模型失败、未知和冲突事实。不能只把模型聊天文字贴入前端就宣称闭环。
2. **完成核心规则与检索。** 对应路线图阶段 2，补齐业务节点、受影响节点重跑、混合检索、时效过滤、段落级引用和知识版本关联。每个结果应能追溯至本次执行采用的事实、规则和来源版本。
3. **完成报告复核与归档。** 对应阶段 3，实现编辑、退回、批准、版本锁定、修改后失效和审计。验收时必须实际验证事实修订后的旧报告处理与历史恢复，而不只是生成 Markdown。
4. **完成试用前的安全及专业门槛。** 身份认证、案件访问控制、组织隔离、日志脱敏、恢复测试和模型数据处理方案仍需落实。具体代码问题：`/health` 返回原始数据库连接字符串，应在接入共享环境前移除，以免泄露凭据。进入 L1 还需香港税务专家验证、30–50 个专家案例及 PRD 规定的关键事实识别完整率 ≥90% 等验收；工程测试通过不能替代这些要求。

路线图阶段 1 的部分后端链路已经实现，但网页工作流及顾问走查证据未齐；阶段 2、3 的主要功能仍有缺口。不能因为历史 L0 工程验收通过而把项目整体视为已到 L1。API key 只解决模型访问凭据，不解决上述业务状态、检索、审批与专业验证问题。

## 本次前端调整

- 移除地区选择、演示/预览字样、虚构预设和固定助手答案。
- 首页只保留标题、输入框及境外股息/梳理事实/查阅依据 3 个快捷问题，案例信息和资料侧栏按需打开。
- 中英文切换、税务图标、手机布局保留；输入草稿按会话隔离。
- 当前提交仅保留本页消息，明确显示“未发送、未生成分析”；手工事实不伪装成已确认的模型事实。
- 对话和事实刷新清空；localStorage 仅保存语言偏好。正式视觉布局不改变后端实际交付等级。
