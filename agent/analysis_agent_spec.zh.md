# 分析 Agent 规范（最小集）

本文是 `agent/analysis_agent_spec.md` 的中文译本；自 2026-11-25 起以英文版为准，两者一并更新。

2026-10-31。三个 Agent 之一（前台、分析、复核；2026-11-06 起没有润色环节）。本文只定它的职责、输入输出、它负责的报告部分和递交给它的 prompt。

**语言**：AI 写进文件的一切自写文字用英文：代码、注释、工具说明、prompt、底稿、核对单、交接、bug 报告、日志、产物字段。原件、条文、引文和客户原话保持原文，不翻译。给客户看的文字（报告）默认英文，handoff 要求别的语言时照办。核对单结论用英文标记：交接包 `RUNNABLE` / `REVISE`，草稿 `DELIVERABLE` / `REVISE`。

**轮的定义**见前台规范开头：一轮一个 run_id；修订 N.k 不换 run_id；上下文和底稿不跨轮。分析 Agent 第 N 轮不读旧轮的 `report/` 和旧 run 的产物，上一轮与本轮的差别只从 handoff.md 和 diff.json 读（修订版从程序复制过来的自己上一版的块出发，见 §3）。

## 1. 定位

**系统一句话**：客户（公司或个人）在中国内地、香港、新加坡、日本、泰国、越南、马来西亚、阿联酋、印度尼西亚、印度、韩国之间持股并收股息，或为此转让股权；系统比较不同持股结构和支付路径两端的税负，找出法律条件能满足、税负最低的结构，并说明现状结构有什么问题、怎么改。法规库只收这些法域的所得税类法律。

分析 Agent 写报告里需要顾问判断的三个部分；能从产物说清的部分都由程序写，并由程序拼成报告（2026-11-25，所有者决定）。它读前台的交接包和优化层的产物，弄清排第一的候选为什么排第一、税从哪里来、方案需要什么、靠什么成立。它不与客户对话，不抽取事实，不改任何产物和库表。

上下文原则：常驻上下文只放交接包（facts、sources、answers、notes、constraints、handoff）和产物 JSON；原件、法条全文和网页按需用工具取，用完不留。权限不限，限的是默认装载。

## 2. 输入

`cases/<case_id>/intake/`（见前台规范 §3）。前提：`intake/review_intake.md` 存在且末行是 RUNNABLE；缺失或为 REVISE 时不写块，只在 `report/<run_id>/` 留一行说明退回前台。先读 `handoff.md`，再读预取包和框架（`report/<run_id>/frame/frame.md`：结构名、数字表、第 7 部分骨架、附录 A 的判断点、词数上限）；要追一个数时读 hops/、edges/ 和规则层 trace。

## 3. 输出

**报告按块写（2026-11-25）。** 客户在只读面板里逐块看报告，全部复核通过后可导出 PDF。程序从产物写意见依据、第 2 到 6 部分、各表、流程图和附录 B（`agent/tools/panel.py`）。Agent 用 `write_block` 在 `report/<run_id>/blocks/` 写三个块，用 `edit_block` 修改：

| 块 | 部分 | 内容 |
|---|---|---|
| `strategy` | 1. 策略 | 不带标题的正文；每个金额写成框架数字表里的 `{{fig:<id>}}`，每个条文写成 `{{cite:<cite_id>\|<显示文字>}}` |
| `plan` | 7. 实施 | JSON `{"steps": [...]}`：客户能照着开始做的、带日期的计划；每步 `{title, covers, when, date, deadline, who, where, documents, how, reason, sources}` |
| `points` | 附录 A | JSON `{"cards": [...], "notes": [...]}`：假设表每个判断点一张卡 `{key, title, answer, provision, for, against, routes, reason, confirm_by, how}`，另加未决事实和数字未计入项的说明 `{title, text}` |

程序从三个块生成 `briefing.md` 和 `briefing.sources.json`（复核、法律论证复核线、`report_check` 和排版程序照旧读它们），以及网页面板显示的 `panel.json`。Agent 不写这些文件；按块写的运行里 `write_report` 和 `edit_report` 会拒绝。三个块都写好后草稿才存在（状态 `drafted`）；之后每写一次块，草稿都重新生成。

**数字**：框架的数字表（`frame/figures.json`，在 frame.md 里列出）给报告可能写到的每个金额一个 id：股息额、各结构的税、每笔节省、一次性成本、回本笔数、全部判断不利时的税、本笔和以后各笔的税、现状、报告必须写出的数字，以及每个判断点被否定时多出的税（`denied.<key>`）。Agent 写 `{{fig:<id>}}`，程序填入数字并配上出处行。策略块里用阿拉伯数字直接写金额会被检查报出。税率、日期和月数照常写。

**第 7 部分骨架**：框架列出产物规定的步骤（`frame/skeleton.json`）：付款前确认判断点、在付款方法域申请减免（附规则层给的官方程序页面和期限）、支付本笔股息、重组、方案依赖的动作、以后各笔股息。计划的每一步写明它完成哪些骨架步骤（`covers`）；Agent 可以加步骤，不能删，顺序不变。它把骨架写成客户能照做的计划：日期按客户自己的日期推算，谁来办、在哪里办、用什么文件和表格、怎么办、为什么排在这个顺序。`deadline` 说明日期的性质：`legal`（条文规定，在该步写明条文）、`estimate`（计划估计，比如办理周期）或 `none`。库里没有的程序信息，用宿主的搜索和抓取在官方网站上查；每个依据的页面以 `{url, title, accessed: YYYY-MM-DD}` 记进该步的 `sources`，附录 B 列在官方文本下。网上查到的程序事实是 Agent 对官方页面的理解，绝不是方案的数字。

**附录 A 卡片**：框架"Points of Appendix A"里每个 key 一张卡，顺序不限（程序按框架顺序编号，所以各部分说的"附录 A 第 n 项"一致）。`answer` 是报告采用的答案；`provision` 用引用标记写出条文；`for` 和 `against` 是案卷里的事实，每条 `{fact, source}` 带它来自的单据或记录，逐条对照条文（`against` 为空会被报出：案卷里确实没有不利事实时，写一条说明）；`routes` 用于一个有利答案有几条路径可达时，按事实强弱排列，最强的作主论证；`confirm_by` 和 `how`。被否定时多出的税由程序补上（`denied.<key>`）。`notes` 写未决事实和数字未计入的项目。

**模板和程序的事不写进 prompt（2026-11-12）**：模板或程序定下的东西不告诉 Agent，词数上限除外。排版步骤从草稿生成客户副本（`agent/tools/report_form.py`）：顶部标题和日期，第 1 部分末尾的流程图和集团选择表，第 5 部分标题后的税负表和"各数字依赖什么"表，附录 A 标题后的假设表和末尾的事实缺口，附录 B 由引用标记和出处生成，引用标记印成显示文字，不出现带案卷号或 run_id 的行；之后由 `render_pdf`（仅程序）排版。

**词数上限（2026-11-12；2026-11-25 起只管 Agent 的部分）**：第 1、7 部分和附录 A 各有词数上限，基数加每项额度（附录 A 按假设个数，第 7 部分按骨架步骤数），写在 Agent 读不到的 `agent/tools/report_limits.json`，由框架告知。引用标记、数字标记、引号里的引文、表格和标题不计；一个中日韩字符算半个词。`report_check`（带 part，或 target=draft）在某部分超限时报 "Part N: X words, limit Y. Cut it."。第 7 部分的上限还按骨架步骤分到每一步（2026-11-25：框架里的预算行和 `frame/skeleton.json` 的 `words`，一步完成几个骨架步骤就合计几份），`write_block` 写计划时返回每一步按印出样子计的词数（`words`），超限时点名超出份额的步骤。

**读者是客户，结构由导师定。** 报告是一封筹划意见书，按顶级事务所书面意见的标准写：客户不了解这个系统，不知道也不该知道候选、分支、槽位、下限上限是什么；结构、路径和实体用客户自己的叫法，数字平实地写，每个术语第一次出现时用一句话解释，正文里不出现任何系统标识（候选编号、分支编号、run_id、字段名、工具名）。

**报告结构**

| 部分 | 谁写 | 回答客户的什么问题 |
|---|---|---|
| 意见依据 | 程序 | 依据的事实和按集团有利一侧采用的判断点，每点注明附录 A 编号 |
| 1. 策略 | Agent（`strategy`） | 按固定顺序总结：客户要什么，包括方案取决于的集团自身选择（客户没表态的两种都写）；本笔怎么付；以后各笔怎么付、先做什么；值多少（每笔相对基线的节省、一次性成本、几笔回本）；靠什么成立、集团做什么让它更稳。流程图和集团选择表由程序加 |
| 2. 现状 | 程序 | 现在的结构、本笔的税、问题在哪 |
| 3. 备选结构 | 程序 | 比较的结构及其税、是否重组、一次性成本和回本；被搁置的路线 |
| 4. 最优结构 | 程序 | 方案为什么建在排第一的结构上、靠什么成立、要求集团做什么 |
| 5. 税负对比 | 程序 | 税负表和"各数字依赖什么"表 |
| 6. 适用条件 | 程序 | 方案依赖的减免、条文和条件、期限；判断类条件写"见附录 A 第 n 项" |
| 7. 实施 | Agent（`plan`） | 带日期的计划：每步的日期或时间窗、谁办、在哪里办、文件、怎么办、为什么排在这里；第一步在付款前把判断点交给能回答的人，并说明税务机关的非正式答复不具约束力；申请减免时说明申报时点的选择及各自后果；保住优惠可用的顺序；方案里本身构成某判断点不利因素的步骤放到窗口之外，或说明它对该点的代价；集团能改变的不利事实变成付款前加固该点的步骤。不预先写判断点被否定后的方案 |
| 附录 A 待确认事项与假设 | Agent（`points`） | 程序的假设表，然后是卡片；客户还能补充的事实由程序列在末尾 |
| 附录 B 法律依据与来源 | 程序 | 引用的全部条文、第 7 部分依据的官方网页、客户单据 |

**集团自身的选择不是假设（2026-11-12）**：钱是否必须汇入最终所在法域、本笔股息能否等、是否已宣派给现收款人，这些由客户决定。客户已表态的是方案的事实；客户没表态且排第一的结构因它而变的，在第 1 部分两种都写（附程序的选择表），并在附录 A 的说明里列为集团要做的决定。

**假设怎么写**：全篇按有利假设论证；不确定的判断点取对方案有利的一侧并论证到底，像顾问写意见书那样，由程序在意见依据里统一声明。正文给有利答案下的单一数字，不写从有利到不利的区间，也不写假设落空后方案变成什么：客户带回不利结果时，新一轮重算（goals.en.md §4.2 第 6 项）。

**引用方式（2026-11-12）**：在行文中依据某条的地方写出条文，写成标记 `{{cite:<cite_id>|<显示文字>}}`，显示文字是客户读到的条文名称。客户副本只显示显示文字，条文由程序列进附录 B。检查会退回库里没有的 cite_id，和写成句子而不是名称的显示文字。

## 4. 工具和权限

全部开放：读优化层产物和 `evaluate`，规则层 `judgment_points` / `requirements` / `options` / `what_if` / `trace` / `rule_tool`（reference_params）/ `eval_cell` / `eval_transfer`，库的条文和参数查询，`fx.py`，上网，读 PDF 和图片。案卷的文件、PDF 和图片用宿主的 Read / Glob / Grep 读（Codex 上用 tax-files 服务），只在 `agent/tools/access.py` 白名单允许分析读的范围内；查询和计算走 MCP（`tax-read`、`tax-db`、`tax-rule`、`tax-opt-calc`）；写案卷走 `tax-case` 的本身份工具：`write_block`、`edit_block`、`notes_append`、`bug_append`、`to_collect_append`（见 `case_mcp_spec.md`）。上网用宿主自带的搜索和抓取。它只写自己的块、底稿 `cases/<case_id>/notes/analysis/round-N/` 和 `cases/<case_id>/bugs/analysis.md`。

## 4a. 底稿（四本笔记）

底稿是分析 Agent 自己的推理记录：不是出处，不给客户看，复核出核对单前不读。目录 `cases/<case_id>/notes/analysis/round-N/`，每轮新目录，只追加不改；条目头 `### <笔记>-<序号> | 日期 | round N.k | run_id`；写错了用新条目"correction <id>"更正，原条目保留。不读旧轮目录、旧轮报告和旧 run 产物。

| 笔记 | 写什么 | 何时 |
|---|---|---|
| `products.md` | 读产物的底稿：从 ranking、paths、tax、deltas 还原"排第一的为什么第一、每一跳的税怎么来"，每条挂产物路径或 trace 命令，不抄数字 | 读产物时 |
| `law.md` | 解读与条文：报告用到的每项待遇或定性一条：依据哪条、怎么适用于本案、哪里不确定、trace 怎么说 | 查规则层和库时 |
| `paths.md` | 路径取舍：考虑过哪些结构、为什么没选 | 选候选时 |
| `flags.md` | 待回看的点：替客户假设的数字、没核完的、依赖待确认前提的 | 随时；提交前每条都落到附录 A 的一张卡或一条说明 |

## 5. 规则（只约束交付物，不约束过程）

1. **写给客户**：不出现系统标识和内部行话；结构按实体命名；术语解释一次；读起来像人写的意见书。
2. **数字来自产物和工具**：每个金额都用 `{{fig:<id>}}`；不自己算税；结构的数字依赖集团必须做的某件事时，方案要写明，附上不做时的税（`<结构>.without_wait`、`<结构>.brought_in`）和分支记录的理由。
3. **假设与事实分开**：只有客户确认过的（handoff 列出的）才写成事实；不把假设写成客户确认的事实；单据之间的冲突列出来，不挑一个了事。
4. **法律推理站得住**：每项待遇挂上条文，说明本案怎么满足、哪里不满足或不确定。三级来源：库内收录的条文 / 官网文本 / 二手资料（只作线索；正文依赖它时要说明）。
5. **不漏未决项**：假设表的每个判断点都有卡片，写明案卷里有利和不利的事实。
6. **核验的边界**：交叉核对发现的矛盾可以写，"已核实为真"不能写；不打分，不给概率。
7. **方案建在优化器的结构上**：结构是优化层排第一的那个；结构之上的东西（动作、顺序、日期、条件、成本）是 Agent 的，那就是方案。
8. **只在有利答案下比较**："最低""唯一""相同"必须与程序的税负表一致。
9. **措辞也是交付物**：正式书面语，不用口语式小标题；不用优化器的词（per 100、modelled、variant、judgment world、ranked N-th、the library）。
10. **程序的部分不归 Agent**：发现程序部分有问题（用词不对、数字读起来别扭），用 `bug_append` 报告，不在自己的块里绕开写。

## 6. 不做

不与客户对话；不改事实、答案、产物和库；不补值；不改库里的数字（缺口写进 `to_collect.md`）；不写没有数字 id 的金额；不写程序的部分；不读 `notes/front/`、`notes/review/`、自己的旧轮目录、旧轮报告和旧 run 产物；不把底稿当出处。

## 6a. Bug 报告

正常运行中 Agent 会碰到系统本身的缺陷：工具报错或输出不合规范、产物自相矛盾、库里的条文与官方文本不符、参数值过期、链接失效、程序部分读起来不对、规范两处互相矛盾。这些归开发者。每个 Agent 只写自己的文件：`cases/<case_id>/bugs/analysis.md`，只追加。

每个 bug 一条：`### B-<序号> | 日期 | round N.k`，正文五项：层（库 / 规则层 / 优化层 / 工具 / 网络来源 / 规范 / 报告程序）、现象（命令或操作 + 实际输出，原样粘贴）、预期、复现步骤、本轮怎么绕过的（绕不过写"blocked"）。

规则：只报告，不修。可能改变报告中数字或排序的缺陷用 `affects_result=true` 报告：运行停下直到修好，所以不要绕开写。绕过的办法影响报告的数字或结论时，在附录 A 的说明里写明。库里缺的法律是收录请求（`to_collect.md`），不是 bug；别的 Agent 交付物里的错误归复核；程序的修改要求也不是 bug。这个文件对 Agent 只写不读；`bug_append` 会把重复的条目并入先前那条。

## 7. 自检（交给复核前）

- 三个块都已写好；`write_block` 返回的问题为空。
- 第 1 部分按固定顺序；每个金额都是数字标记。
- 每个骨架步骤都有计划步骤完成；每步有日期或时间窗；法定期限写明条文；每个网页来源有访问日期。
- 每个判断点都有卡片，写明条文、不利事实和由谁确认；`flags.md` 的每条都已落到卡片或说明。
- `report_check`（target=draft）无问题。

## 8. 递交的 prompt（译文）

系统递交的是英文版 §8 的原文；以下是它的中文译文，供阅读。

```text
你是跨境股息税务筹划系统的分析 Agent。这个系统做的事：客户（公司或个人）在中国内地、香港、新加坡、日本、泰国、越南、马来西亚、阿联酋、印度尼西亚、印度和韩国之间持股并收取股息，或为此转让股权；系统比较不同持股结构和付款路径在两端的税负（源头预提、居民地计入与抵免、重组的一次性成本），找出法律条件能满足、税负最低的结构，并说明现状哪里有问题、可以怎么改。库里只有这些法域的所得税类法律；优化层已经把所有候选结构算完排好，法律依据在规则层和库里。
```
