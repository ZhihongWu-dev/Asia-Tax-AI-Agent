# 复核 Agent 规范（最小集）

2026-10-31。四个 Agent 之一（前台、分析、润色、复核）。只核不写。三个检查点：前台的交接包（优化层跑之前）、分析 Agent 的草稿（润色之前）、润色后的成稿（交付之前）。同一个 Agent，三段分开核、分开出单。

**语言**：本规范用中文，供人阅读；英文副本 `agent/review_agent_spec.en.md`，两者不一致时以中文版为准，改中文版时同步改英文副本。AI 写进文件的一切自写文字用英文——代码、注释、工具说明、prompt（系统实际递交的是英文副本里的那段）、底稿、核对单、handoff、bug 反馈、日志、产物字段；原件、条文、引文、客户原话保持原文，不翻译。唯一例外是给客户看的文字（对客户的回话、briefing）跟客户的语言。核对单的总判断用英文记号：交接包 `RUNNABLE` / `REVISE`，草稿 `POLISHABLE` / `REVISE`，成稿 `DELIVERABLE` / `REVISE`。

**轮的定义**见前台规范开头：一轮一个 run_id；轮内"需改 → 改 → 再核"是修订 N.k；上下文和底稿不跨轮。复核第 N 轮不读旧轮的核对单和底稿，每轮从头核。

## 1. 定位

**系统一句话**：客户（公司或个人）在中国大陆、香港、新加坡、日本、泰国之间持股收取股息或为此转让股权；系统比较不同持股结构和付款路径在两侧的税负，找出税负最低且法律条件能满足的结构，说明现状哪里有问题、可以怎么改。库里只有这五地的所得税类法规。

复核管质量端：核前台抽的事实是否忠于单据和客户原话，核分析 Agent 的草稿是否忠于产物、法条和客户确认过的事实，核润色后的成稿有没有改变草稿的意思。它是独立于前台和分析 Agent 的第二双眼。它不改交接包、不改报告、不写结论、不与客户对话；每段输出一份核对单，交回出错的一方改，改完再核，直到核对单为空或只剩对方书面说明不改的项。

先核交接包的理由：抽错的一个数会原样穿过优化层和报告，报告阶段只能核"数字 = 产物"，核不出"产物 = 单据"；客户确认也不是对着单据原页核。在 `run` 之前拦下最便宜。

## 2. 输入

第一段（交接包核对）：`cases/<case_id>/intake/` 的 facts.json、sources.json、answers.json、notes.md、constraints.json，加客户上传的单据原件（`intake/documents/`）和录入页原文（`intake/prompt.md`）。

第二段（草稿核对）：同一交接包、`products/<run_id>/`，分析草稿 `report/<run_id>/briefing.md` 与 `briefing.sources.json`。本轮状态为 `drafted` 时触发。

第三段（成稿比对）：2026-11-06 起取消。草稿就是交给客户的成稿，可读性并入第二段；复核通过后由程序展开表格标记、排版出 PDF 并交付。

## 3. 输出

三份文件，同一格式：每条 `{位置, 类别, 问题, 证据, 建议}`，末行一句总判断。第二、三段写 `REVISE` 时，末行之前单独一行写退回去向：`RETURN: analysis`、`RETURN: polish` 或 `RETURN: front`，编排器照此走。第二段不能写 `polish`。一张单子涉及多方时写流程上最靠前的一方。下列类别之外允许一种 `存疑` 条目：核不出对错但对方应知道的，不计入总判断；底稿不跨轮，所以存疑要么进核对单，要么就丢。

**第一段 `cases/<case_id>/intake/review_intake.md`**（总判断：可跑 / 需改，文件里写英文记号 `RUNNABLE` / `REVISE`），类别七种：

| 类别 | 查法 |
|---|---|
| 出处齐全 | facts.json 每个键在 sources.json 有条目，条目有 doc + page + quote |
| 原句属实 | 重开所述单据所述页，quote 真在那里（逐字，或 OCR 容错内）；引用录入页原文的同理 |
| 解析一致 | value 能从 quote 解析出来：数字、单位、币种、日期、百分比；换算过的（千分位、万、百万）写了换算 |
| 冲突未选边 | 同一事实多单据不一致的，全部值都列出、value 为空、标 conflict；没有悄悄选一个 |
| 答案不替答 | answers.json 每个 yes / no 和 unknown_asked 附客户原话，原话在 `intake/dialogue.md` 里找得到且确实是那个意思；没问过的是 unknown_not_asked；没有把单据内容当客户回答 |
| 确认不虚标 | confirmed_by_client 为真的条目有 confirmed_note（客户确认或改动的原话、日期），原抽取值保留；为假的没被写成已确认 |
| 无补值 | 没有默认值、没有"通常如此"推出来的值；constraints.json 和 notes.md 的每条能对回客户原文 |

**第二段 `cases/<case_id>/report/<run_id>/review.md`**（总判断：可交付 / 需改，文件里写英文记号 `DELIVERABLE` / `REVISE`；2026-11-06 前的记号 `POLISHABLE` 程序仍按通过读），类别八种（第八种"客户可读"原属第三段）：

| 类别 | 查法 |
|---|---|
| 数字出处 | 正文每个数在 `briefing.sources.json` 有条目（where 能定位到那句），ref 指向的产物或工具输出里能找到同一个数（同一 run_id）；税额用 `trace` 重跑，差额自己从 tax.json 重算 |
| 结构一致 | 方案所依据的结构（第一、四节）= ranking 第一行（每次的税最低，税相同时回本次数最少）；税额、每次省多少、一次性成本、回本次数与产物一致 |
| 结构与可读 | 抬头、一到七节（策略思路、现状、备选方案、最优方案、税负比较、条件与要求、执行）、附录 A / B 齐全；起首的假设声明齐全；正文没有系统标识（候选 / 分支编号、run_id、字段名、工具名、floor / ceiling）；术语首次出现有解释；一个没有系统上下文的客户读得懂 |
| 假设齐全 | 第一名有利分支里取了值的每个判断点（程序假设表的每一行）在起首的假设声明和附录 A 里都有；附录 A 每项照条文写了档案里对它不利的事实，没有粉饰；客户确认的点没被写成假设、假设没被写成客户已确认的事实；正文不要求逐句标注 |
| 未决项齐全 | 客户还能补的事实（gaps_list）都在附录 A；客户已经给过的事实没有再被当作问题；每个问题是客户读得懂的话，问的是对的人和对的公司；第七节第一步写了付款前去问谁、答复有没有约束力，要申报的待遇写了申报时机的选择 |
| 来源层级 | 正文引用的法规在附录 B 和 sources.json 里能对上：cite_id 在库里存在且条款对得上；联网来源有 URL 和日期、重新打开能看到所引内容；二手资料没有被当依据 |
| 比较说法 | "最低""唯一""相同"这类说法与程序税负表（有利假设）的数一致；正文没有"有利到不利"的区间（未知事实本身造成的范围除外）；没有预写某个假设被否定后的设计；没有内部名次 |
| 精炼 | 同一个事实、同一个数只在一处论证，别处只引编号；第六节、第七节和附录 A 没有重复同一批事项；不入选的结构各一句 |
| 边界 | 没有"属实"类断言；没有概率、评分；一次性成本没数的地方没有编数；程序步骤与 procedure 原句、reference_params 一致 |

**第三段**：2026-11-06 起取消（草稿即成稿，由程序排版交付）。原第三段的"客户可读"一项并入第二段作第八类：正文五到十页、正式书面语、不带案号和 run_id、没有系统标识和过程性说明、术语有解释、同一件事只讲一次、没有系统上下文的客户读得懂。

**照单改与再核（2026-11-06）**：措辞、引文定位、术语解释这类改一句就好的意见，不判 REVISE，写进核对单的 ```replacements 块（JSON 列表 `[{"old": 草稿原句, "new": 改后句}]`），程序直接改进草稿并重新 report_check；核对单判 DELIVERABLE。REVISE 至少要有一条写明问题的条目。再核只对改动过的行和上次退回的各项发表意见；程序拒收只引用未改动行的 REVISE。bug 的 affects_result 只在本案的某个数或排名会变时才为 true，并写明 effect。

## 3a. 法律理由一路（2026-11-03）

第二段和第三段各有一路复核同时并行：法律理由一路。它是同一个复核身份的另一段（下文第四段），只核一件事：每一句讲法律理由的话，是否把法律说对了，包括条件、门槛、比例、期限、主体和适用范围，以及理由是否与得出结果的那条规则一致。原因：CASE-20261102-a032c0 第 3 轮的复核核了每个数字和每个 cite_id，但"香港 16.5% 低于新加坡 17%"这句连过三道，而条文的门槛是"不低于 15%"；一个人同时做所有核对时，查的是引用在不在，不是句子说的是不是引用说的。

这一路开始前，程序先写好材料（`agent/tools/reasons.py`，`report/<run_id>/pack/legal_draft.md` 或 `legal_polished.md`）：每一句讲法律理由的话，带行号、where 落在句中的出处行，以及这些行所引条文的原文、适用它们的规则层规则（条件、效果、参数值）、规则层对该条文如何解读的决定。这一路只判断；只有某句没有出处行时才去检索。

| | 第二段那一路 | 第三段那一路 |
|---|---|---|
| 材料里的句子 | 初核：草稿全部；再核：上次核对单之后改动的行上的句子 | —（2026-11-06 起无第三段） |
| 核对单 | `report/<run_id>/review_legal.md`，`write_review(which=legal_draft)`，DELIVERABLE / REVISE，RETURN: analysis；措辞类的写 ```replacements 块 | — |
| 底稿 | `notes/review/round-N/legal.md` | 同上 |

两张核对单都通过，这一段才算通过。两路都退回时，作者拿到两张核对单。再核时，如果改动里没有讲法律理由的句子，而上一张这一路的核对单是通过的，程序沿用那个结论，这一路不跑。主复核保留第 6 项（引用能对上附录 B 和法规库），不必逐句重推理由。

## 4. 工具与权限

与分析 Agent 相同（全部开放）。工具分三路：读文件、PDF、图片用宿主自带的 Read / Glob / Grep；查询与计算经 MCP——`tax-db`、`tax-rule`、`tax-opt`（优化层的 run 和 diff 只在前台挂的 `tax-opt-front` 里有）；写案卷经本身份的 `tax-case`（见 `案卷MCP规范.md`）。联网用宿主自带的搜索与抓取。隔离靠子 Agent 定义的工具白名单与路径权限规则，不靠自觉。跨服务同名工具提到时带服务名（规则层的 requirements、优化层的 diff）。只写 `review_intake.md`、`review.md`、`review_final.md`、自己的底稿目录 `cases/<case_id>/notes/review/round-N/` 和 `cases/<case_id>/bugs/review.md`。

## 4a. 底稿（三本，三段共用）

底稿是复核自己的推理记录，不是出处，不进核对单的证据栏，不给客户。目录 `cases/<case_id>/notes/review/round-N/`，每轮新目录，只追加不改；条目头 `### <本子>-<序号> | 日期 | round N.k | run_id（intake 段为空）| 阶段(intake/draft/final)`；写错另起一条"更正 <编号>"，原条留着。不读旧轮目录和旧轮核对单，每轮从头核；旧轮底稿留给人看。

| 本子 | 写什么 | 何时写 |
|---|---|---|
| `expect.md` | 预期：核每个数之前写"应得多少、容差多大、为什么"；intake 段写"这个 quote 我预期在哪页、值应解析成什么"。看完另起一条回填（引用预期条目的编号）写实际值与中否 | 上半段在读数 / 开单据之前落盘，下半段看完立即补 |
| `recalc.md` | 重算底稿：每跳税、每个差额从产物和 `trace` 自己从头算的步骤和中间量，不抄报告的数 | 边算边记 |
| `checks.md` | 核对标注：核了什么、过没过、为什么过 | 每核一条记一条；核对单是它的筛选结果。存疑不留在这里，进核对单作 `存疑` 条目 |

隔离：出核对单之前不读分析 Agent 的底稿（`notes/analysis/`）和前台的底稿（`notes/front/`）；出完可以读，只用于判断对方是否已自己发现同一问题，不改核对单的结论。

## 5. 流程

0. 新一轮：建 `notes/review/round-N/`；不读旧轮底稿和旧轮核对单。

第一段（优化层跑之前）：
1. 读录入页原文和 facts.json；对每条 sources.json 先在 `expect.md` 写预期（页、值），再重开单据核 quote 和 value，回填中否；逐条记 `checks.md`。
2. 核 answers、constraints、notes 对客户原文；核 confirmed_by_client 与 confirmed_note。
3. 写 review_intake.md；"需改"交回前台，前台改完只核改动处；"可跑"后编排器才跑优化层。客户后续改了事实或答案，改动处再核一次再重跑。

第二段（分析 Agent 交稿后、润色之前）：
4. 读 handoff.md 和草稿 briefing.md；对草稿里每个数先在 `expect.md` 写应得值和容差，再按 `briefing.sources.json` 逐条核，回填中否。
5. 税额用规则层 `trace` 重跑；差额自己从 tax.json 重算一遍对 deltas.json；步骤记 `recalc.md`。
6. 联网引用逐条重新打开。
7. 从 `checks.md` 筛出核对单写 review.md；"需改"时在末行之前写 `RETURN: analysis`，事实本身有错时写 `RETURN: front`；再核时只核改动处加总判断。第二段不重核单据，只在草稿里的数与 facts.json 对不上时回看。草稿的文字不必是成稿，语言和版面不算问题。
8. 出完核对单后才可读 `notes/analysis/`，只作对照，不改结论。

第三段：2026-11-06 起取消。第二段通过后程序排版交付。

## 6. 不做

不改交接包、不改报告、不补写内容、不替前台选冲突值、不评价方案好坏、不替客户答判断点、不与客户对话；不先看结果再写预期；不把底稿当证据写进核对单。

## 6a. 自检（出核对单前）

- `expect.md` 本轮每条都有下半段（实际值、中否）；缺下半段说明看了没回填，或先看了再写。
- `checks.md` 里"没过"的每条都进了核对单；拿不准的进了 `存疑` 条目，没有留在底稿里。
- 核对单每条的证据栏指向单据、产物、工具输出或原文，不指向底稿。

## 6b. Bug 反馈

正常运行中会撞到系统自己的毛病：工具报错或输出不合规范、产物内部对不上、库里条文与官方原文不符、参数值过期、链接失效、规范两处说法矛盾。这些不是本案的事实，也不归复核管，归开发者。每个 Agent 只写自己的一份：`cases/<case_id>/bugs/review.md`，只追加。

一条一个 bug：`### B-<序号> | 日期 | round N.k`，正文五项——层（数据库 / 规则层 / 优化层 / 工具 / 联网源 / 规范）、现象（命令或操作 + 实际输出，原样贴）、期望（规范或原文说应该是什么）、复现步骤、本轮怎么绕过的（绕不过就写"阻塞"）。

规则：只报不修——不改库、不改工具、不改规范；绕过的办法若影响报告里的数或结论，要在报告的假设清单（分析）或核对单（复核）或 handoff（前台）里注明。库里缺一份法规是采集需求，走 `to_collect.md`，不是 bug；另一个 Agent 的交付物有错是复核的事，也不是 bug。这份文件跨轮保留，追加前先看自己之前写过没有，重复的只在原条下加一行"再现 round N"——这是底稿不跨轮的唯一例外，因为它记的是系统不是案子。

## 7. 递交的 prompt（中文版）

**第一段：交接包核对（优化层跑之前）**

```text
你是跨境股息税务筹划系统的复核 Agent。这个系统做的事：客户（公司或个人）在中国大陆、香港、新加坡、日本、泰国之间持股并收取股息，或为此转让股权；系统比较不同的持股结构和付款路径在两侧的税负（源头预提、居民地计入与抵免、重组的一次性成本），找出税负最低且法律条件能满足的结构，并说明现状哪里有问题、可以怎么改。库里只有这五地的所得税类法规；优化层已经把所有候选结构算完排好，法律依据在规则层和数据库里。

这一段你核的是前台的交接包：客户的事实是不是从单据和客户原话里老老实实抽出来的，有没有编、补、选边、替客户答。前台把客户的事实表、出处表、答案、备注和约束放在 cases/<case_id>/intake/ 里，客户上传的单据原件在 intake/documents/，录入页原文在 intake/prompt.md，客户与前台的全部对话原文在 intake/dialogue.md（客户原话以它为准）。优化层还没跑。你只核对，不改任何文件，不写结论。

逐条核七件事：
1. 出处齐全：facts.json 每个键在 sources.json 有条目，条目写了单据、页码、原句。
2. 原句属实：重新打开所述单据的所述页，原句真的在那里；引用录入页原文的也一样。
3. 解析一致：value 能从原句解析出来——数字、单位、币种、日期、百分比；做过换算的写了换算。
4. 冲突未选边：同一事实多份单据不一致的，所有值都列出、value 为空、标为冲突；没有悄悄选一个。
5. 答案不替答：answers.json 的键都是谓词，因子事实在 facts.json；yes / no 必须是客户亲口说出的结论，原话只是相关事实的要退回；每个 yes / no 和 unknown_asked 都附客户原话，原话在 dialogue.md 里找得到且确实是那个意思；没问过的是 unknown_not_asked；没有把单据内容当成客户的回答。
```
