## 0. 为什么要做

四个 agent 读三类材料：法规库（database/）、优化层产物（cases/<案卷>/intake/products/<run_id>/）、案卷（intake/ 下的事实、出处、对话、单据）。现在它们靠宿主的 Glob / Read / Grep 和各层 MCP 的整块读取工具自己找、自己读。2026-11-03 对 CASE-20261102-a032c0 的实测：

| 观察 | 数字 |
|---|---|
| 分析节点，qwen3.8-flash，22 分钟内 | 98 次工具调用，一字未写 |
| 其中找文件 | 21 次 Glob：9 次被守卫拒绝（搜整个案卷），多次因 Windows 下带子目录的匹配写法落空；5 次 Grep |
| 读进上下文的工具返回 | 累计 531,446 字符，约 14 万 token；单次最大 62,545（宿主为超长返回另存的文件）、open_items 56,071（读了两次）、requirements 39,034 和 39,003、brief.json 33,674 |
| 模型思考 | 212,349 字符，可见文字 186 字符：每一轮都带着十几万 token 的上下文重新想一遍 |
| 同一节点，qwen3.8-max | 5,197 秒，114 轮，172,349 个输出 token；46,480 字符的出处表整张发了 3 次 |
| 一次运行的产物 | 47 MB：edges/ 3,876 个文件 43 MB，graph.json 2.3 MB，deltas 247 KB，tax 206 KB，gap 135 KB |
| 法规库 | 156 份文件，18,411 条条文，2,420 万字符；条文长度中位数 360 字符，p90 1,877，p99 9,334，最长 650 万（整部法被切成一条）；1,717 条超过 2,000 字符 |
| 案卷单据 | 16 份，1.6 MB，PDF 和 PNG 扫描件 |

结论：慢的根源不是模型，是"找不到"和"读太多"。换成更快的模型后输出快了，总时间没有少。文献对这一现象有一致的解释：输入越长，模型表现越差且不均匀，哪怕信息就在上下文里 [R18]；agent 的工具应当"返回省 token 的信息"，臃肿的工具集本身就是常见故障 [R19]。

## 1. 定位与原则

1. **铲子，不是作者。** 检索服务是程序：切片、建索引、找、取、核对，全部确定性；同样的索引版本和查询永远得到同样的结果。它不写报告，不做判断，不替模型改写问题。对应 `目标.md` §4.3 第 8、9 条。
2. **只返回原文和原值。** 法条逐字，产物数值原样，客户原话逐字。索引字段（标题路径、模板口述）只用于匹配，不作为返回正文。任何生成文字都不进返回体。
3. **不返回分数。** 返回名次、命中通道、有效期和语言，不返回相似度或重排分值，避免分数流进报告（`目标.md` §4.1 第 1 条禁止评分）。
4. **联网内容不进索引。** 索引只覆盖库、产物、案卷。agent 联网查到的东西照旧只能进报告并标层级（§4.3 第 9 条）。
5. **能力只加不减。** 新工具是增加；宿主的 Read / Glob / Grep 保留，守卫规则不变（§4.3 第 11 条）。让 Glob 变得没必要，而不是禁止它。
6. **出处一体。** 每个返回片段有稳定编号，编号就是出处表的 `ref`；交付前程序核对草稿里的每个数字和引文都出现在被引片段里。编号是内部标识，客户文字里不得出现（§4.4 第 14 条），润色负责去掉，`report_check` 的泄漏模式要加上编号格式。
7. **按材料选方法。** 三类材料的性质不同，不用一套向量检索去套。方法的采用以本项目的评测为准，不以论文的数字为准（§12）。
8. **时效。** 法条按交易日期取当时有效的文本；日期早于库内覆盖时明确答"未覆盖"，不拿现行文本代答（I 轮 I20 的结论，归档的 `official/` 知识层已有实现）。

## 3. 总体结构

```text
A 索引层（程序，各材料在各自的时机建）
   法规库   database/tools/build.py 末尾 → database/index/（index.sqlite + vec.npy）
   产物     优化器 run 结束后，编排器调用  → cases/<案卷>/intake/products/<run_id>/index/
   案卷     put_document / write_intake 时   → cases/<案卷>/intake/index/
B 检索服务（MCP，按身份挂载：tax-read-front / -analysis / -review / -polish）
   map · search · get · expand · ground · pack
C 预取包（程序，节点开始时生成，任务文本直接给路径和文件清单）
D 出处贯通（编号 = ref；report_check 核对数字和引文都在被引片段里）
E 评测（金标准、指标、消融、端到端；只按指示跑）
```

设计上采纳 [R19] 的混合策略：必定要用的材料预取（C），其余由 agent 按需用工具取（B），两者都走同一套编号和出处。

## 4. 法规库检索

复活归档的知识层（`archive/old-model-2026-10-31/official/tools/graph.py`、`search.py`、`eval_search.py`，共 1,428 行）并移到 database/ 上。它已实现单元切分、层级标题、显式引用边、FTS5、BGE-M3 向量、倒数排名融合、语言均衡、个性化 PageRank 扩展、时效三值和引文锚定，并在本项目的金标准上做过评测（I 轮综合 §4、§6）。本节只写沿用、调整和新增。

### 4.1 单元与上下文

- 条文（clause.csv 一行）是引用单位；长于约 1.4 倍上限的条文再切成单元：先按结构标记（款、项、段、编号），再按句末，小段合并到上限，仍超长的硬切。上限中文、日文、泰文 260 字符、英文 700 字符（约 100 个英文词的阅读量），沿用 graph.py 的 `split_units`，即 I 轮评测所用的值。单元必须能回到原文区间（起止偏移），返回时给的是原文区间，不是改写。
- 每个单元带一个只用于匹配的 `header`：法名、编/章/节/条的路径、条标题、文件内定义的简称。这是确定性的"上下文增强"：Anthropic 的上下文检索用模型给每块写 50 到 100 个 token 的说明，前 20 条的漏检率从 5.7% 降到 3.7%，再加 BM25 降到 2.9%，再加重排降到 1.9% [R4]；法律语料上，给块附上文件级摘要能显著减少"检索到了错误文件"的错误 [R11]。本库用层级标题而不是模型摘要，因为标题是原文的一部分，可核对。模型写的说明（`gloss`）2026-11-03 用户定：等全库采集到位后再开；索引里预留 gloss 字段和按文本哈希的缓存，开的时候只补说明，不重建其余索引；它只进匹配字段，永不返回。
- 切分方式以结构为准，不做语义切分：36 种切分法、6 个领域、5 个嵌入模型的系统比较里，保留结构的切分明显优于定长切分，法律和数学领域以"段落成组"最好 [R7]；语义切分的算力开销没有换来稳定的收益 [R9]；法律文件按条款边界切，边界精度 100% 对递归切分的 7.7%，交叉引用保留 97.6% 对 0% [R6]。块大小没有通用最优值，事实型问题宜小（64 到 128 token），需要上下文的问题宜大（512 到 1,024 token），且随嵌入模型而变 [R8]：本库单元小，父级条文按需取，两头都顾到。

### 4.2 通道与融合

1. **精确通道**：条号（"第十条"、"section 15(1)(b)"、"Article 10(2)"）、cite_id、参数 id、口径 id、法名简称。命中即排首位，不参与融合。规则和参数的查询应走这条通道：I 轮评测里以我们自造的裁量项名作查询时所有配置都弱（R@10 ≤ 0.13）。
2. **BM25**：SQLite FTS5，中文按字二元组、其余按词，`header` 和正文两个字段。零样本下 BM25 是强基线，稠密检索跨领域常输给它 [I1]。
3. **稠密**：BGE-M3（已在本机缓存，568M 参数，8,192 token，中英俱佳，I 轮用它把 params 集 R@10 从 BM25 的 0.187 提到融合后的 0.353）。2026-11-03 用户定只用 BGE-M3，不做模型对比；Qwen3-Embedding（MTEB 多语言 0.6B 64.33、4B 69.45，BGE-M3 59.56 [R1]）留作以后的选项。
4. **融合**：倒数排名融合，k = 60，不校准分数 [I2]。**语言均衡**是必要的：等权融合会把跨语言候选全部压到同语言词面候选之后；I 轮评测里中文金标 R@10 从 0.032 升到 0.318，跨语言（条约中→英）R@10 到 0.717。
5. **图扩展**：只沿显式边（contains、cites、same_provision、substitutes）做个性化 PageRank，加节点特异性降权，权重 0.5（I 轮评测 R@10 0.353 → 0.377，跨语言 0.717 → 0.825）。不建由模型抽取的边：覆盖不全且无法逐条核对 [I13]。文献里图检索的位置也清楚：简单的事实查找上普通检索相当或更好，图在多跳推理和综合上占优 [R13、R14]；法律问答上混合方案胜过纯图方案，纯图丢失文本语义 [R15]。所以图扩展只在命中之后、作为补充通道，默认深度 1。
6. **重排序**：对融合后的前 50 条用交叉编码器重排，取前 k。用 Qwen3-Reranker-0.6B（2026-11-03 用户定，不做对比）：与 bge-reranker-v2-m3 同为 0.6B，多语言检索子集 MMTEB-R 66.36 对 58.36、英文 MTEB-R 65.80 对 57.03、长文档 MLDR 67.28 对 59.51，中文 CMTEB-R 71.31 对 72.16 基本持平 [R1，作者自测]；32k 上下文，长条文不必截断；接受任务说明。库里日文条文 10,353 条、英文为主的香港新加坡条文和中英条约占多数，多语言更强合适。重排序必须过评测再开：合同法律语料上有报告称通用重排器反而把 Recall@64 从 61.06 压到 47.54 [R10 的二手报道，待核]。重排器按材料类型各有开关。
7. **时效**：`as_of` 过滤文件和参数的生效区间；早于覆盖答 NotCovered 并说明原因 [I20]。
8. **跨语言**：条约中英表达用 same_provision 边相连；查询扩展用术语词典（rule/variable.csv、predicate.csv 的中英释义，加库里文件自带的"以下简称"）。跨语言靶子主要靠显式边和稠密通道，词面无效 [I4]。
9. **可选实验**：晚切分（先把整条或整节送进长上下文嵌入模型，再按单元池化，无需训练 [R5]）；BGE-M3 的稀疏权重作第四通道。都只在评测有收益时采纳。

### 4.3 返回

命中项：`id`（= cite_id 或 unit_id）、法名、条标题、语言、有效区间、原文片段（单元原文，不超过 `max_chars`）、`other_lang`（同条款的另一语言表达编号）、`parent`（所属条文）、名次、命中通道。`get(cite_id)` 取整条，长条文按 offset 分页，与 tax-db 的 `clause` 一致。

## 5. 产物检索

### 5.1 类型化记录

程序在 run 结束后把产物切成记录，每条有稳定编号 `<run_id>:<type>:<key>`：

| type | key | 来源 | 字段（用于过滤） |
|---|---|---|---|
| structure | cand_id | paths.json、brief.json、ranking.json | 路径、动作、重组方式、签名、名次 |
| branch | branch_id | tax.json、branches.json | cand、假设答案、floor / ceiling、完整性 |
| hop | branch_id/edge_id | hops/、tax.json 的 hops | tail、head、法域、各项税 |
| cell | branch_id/edge_id/slot_key | edges/ 的 items | 法域、槽位、规则、cite_ids、状态、needs |
| rule | rule_id（本 run 用到的） | edges/ 的 rules_applied | 法域、槽位、cite_ids、口径 |
| point | key@jur | brief.json、open_items.json | about、changes_rank、两种答案下的第一名、at stake、阻塞的分支 |
| scenario | scenario_id | brief.json、scenarios.json | against、各结构金额、第一名 |
| requirement | cand_id/node | requirements/ | 变量、谓词、来源规则 |
| open_item | key | open_items.json、gap.json | kind、client_supplies、问题 |
| transfer | cand_id/序号 | transfers/ | 对价、成本、税、印花、标记 |
| exposure、penalty | cand_id 或 branch_id | deltas.json、penalty/ | 税、利息、罚款 |
| past_payment | date | past_payments.json | 金额、矛盾、可退 |
| basis | cand_id | hops/、transfers/ 的 cite_ids 加法规库原文 | 这个结构的格和转让所依据的全部条文：cite_id、标题、条号、适用它的规则、所在的格、原文（每条前 800 字符）；定税率、免税、反滥用的在前，居民判定的在后。2026-11-03 加：分析 agent 原本一条条去取条文核对 |
| diff | 字段 | diff.json | 对上一 run 的名次变动、区间变动 |

每条记录带：过滤字段；一句英文**口述**（程序模板生成，≤ 300 字符，只用于 BM25 和可选的稠密匹配，例如 "branch c5.b0: cn:company > hk:company > sg:individual, all points favourable, tax 700,000 CNY (5.0 per 100), hops cn>hk wht 5%, hk>sg 0"）；一张**卡片**（≤ 600 字符，字段和数值原样）；全文指针（文件路径 + JSON 路径）。数值永远从产物原值复制，不重算（`目标.md` §4.3 第 9 条）。

### 5.2 图与检索

- 边：structure → branch → hop → cell → rule → clause（跨到法规库的 cite_id）；point → 阻塞的 branch、两种答案下的第一名；requirement → 变量 → 事实键；scenario → 各 structure 的金额；transfer → structure。
- 查询先解析编号和过滤词（cand、branch、key@jur、法域、槽位、情景），能用过滤直接定位的就不走文本匹配：事实型查找上图和向量只会添噪声 [R13]。其余走口述上的 BM25（可选加稠密），再对命中项按请求做深度 ≤ 2、不超过 30 条的展开。这是"结构 + 单元格"两级检索的思路：先给模式，再取所要的格 [R16]；在推理时按任务选用图、表或目录结构 [R17]。
- **层级返回**：默认返回卡片；`get(id)` 返回整条记录；`expand(id, kinds, depth)` 返回邻居卡片。open_items（56 KB）、requirements（39 KB 一个）、graph.json（2.3 MB）这类文件不再被整块读进上下文。
- brief.json 仍是入口，但它的摘要进预取包（§9），agent 不必再整份读。

### 5.3 与现有切片工具的关系

## 6. 案卷检索

### 6.1 事实、出处、对话、笔记

- 记录：facts.json 的每个键（值、单位、出处条）；sources.json 的每条（key、doc、page、quote）；dialogue.md 的每一段（#n，逐字）；answers.json 的每个判断点（值、引文）；notes.md 的每条；constraints、to_collect 的每条。编号 `<案卷>:fact:<key>`、`:source:<n>`、`:dialogue:<n>` 等。
- 检索走字段 + BM25。对话段和引文逐字返回。

### 6.2 单据

- `put_document` 时由程序解析一次，按 sha256 缓存：有文本层的 PDF 取文本层并抽表（PyMuPDF）；扫描件和图片用 Qwen3-VL-4B-Instruct 识别（Apache-2.0，本地权重，贪心解码，同一页永远得到同样的文字），每页一次，同时给出文字和以 HTML 写出的表格 [R26]。2026-11-03 用户定：不用百度的任何东西（PaddleOCR、PaddlePaddle，以及内置 PaddleOCR 模型的 MinerU、RapidOCR），尽量用国际认可的模型。按 OmniDocBench 的方法论（页级和元素级 [R22]）在本项目的单据上抽查识别质量，记入评测记录。
- 索引单位：页（文本块按阅读顺序）和表格单元格（表号、行头、列头、值）。单元格索引针对对账单和报表，agent 可以直接问"2024 年 6 月到账金额"而不必读整页。带文本层的 PDF 的表格由 PyMuPDF 抽出；扫描件的表格来自识别模型写出的 HTML 表。
- OCR 文本是**派生物**，不是出处：出处仍是"单据 + 页码"，返回时标 `derived: ocr` 和置信度等级（高 / 中 / 低，不给分数）。agent 需要时仍可用宿主 Read 看页面图像。引文落地（§10 `ground`）对单据允许容错匹配，并把匹配到的原文区间一起返回，由复核判断。
- 不做：页面图像的多向量检索（ColPali 一类 [R24]）。每个案卷十几份单据，文本索引足够；案卷到几百页时再评估。

## 7. 查询理解与纠错式检索

全由程序完成，不在服务内调用模型。

1. **路由**：先识别编号和条号（精确通道）；再抽过滤词：法域（中英名和代码）、cand / branch / key@jur、槽位、日期、情景、文件名；只有过滤词就走结构化查找；否则走混合检索加重排。这是 Adaptive-RAG "按问题复杂度选路径"的思路 [R21]，但用规则而不是分类器。
2. **批量**：`search` 接受多个查询，一次调用返回各自的命中，减少轮数。
3. **扩展**：术语词典做中英互扩（受益所有人 / beneficial owner、常设机构 / permanent establishment 等）；一个词查不到时拆成更短的词，列在 relaxed 下（tax-db 的 `find` 已这样做）。
4. **纠错**：命中为空或全部过滤后为空时，程序按固定顺序放宽：去掉最弱的过滤词 → 放宽语言 → 拆词，最多两次；仍为空返回 `not_found` 和 `tried`（试过什么），绝不猜。CRAG 用评估器判定检索质量再纠正 [R21]；本服务用程序规则，因为模型自评"上下文够不够"不可靠 [I22]。
5. **不做**：模型改写查询、HyDE 一类生成伪文档。agent 自己可以换问法。

## 8. 上下文预算与去重

- 每次返回默认不超过 4,000 字符，卡片不超过 600 字符；超出部分用 `cursor` 续取；`get` 默认 6,000 字符一页，带 `total_chars` 和 `offset`。
- **会话去重**：服务进程的生命周期就是一次 `claude -p`，服务记住本会话已返回过的编号；再次命中时只返回编号和"已于第 n 次调用返回"，除非 `full=true`。这是"工具结果清理"的服务端版本：Anthropic 把它列为最轻、最安全的上下文压缩 [R19]。
- 预取包不超过约 9,000 token（36,000 字符；超出时从末尾整节略去并列出名字，不从中间截断）；任务文本里的文件清单不超过约 1,500 token。
- 依据：18 个模型的测试里表现随输入长度一致下降，干扰项加剧下降，约 300 token 的聚焦输入全面优于 11.3 万 token 的整段输入 [R18]；长上下文和块检索的比较里，块检索落后，摘要式检索接近长上下文 [R20]，所以预取包必须是好的摘要，而不是原文堆砌。Anthropic 对小于 20 万 token 的知识库建议直接塞进提示 [R4]：法规库 2,420 万字符、产物 47 MB，都远超这条线，检索不可省。

## 9. 预取包

节点开始前由编排器调用程序生成，写到 `cases/<案卷>/report/<run_id>/pack/<节点>.md`，任务文本给出路径，并内联文件清单（`map` 的输出）。每份包的每一项都带编号，agent 引用时直接用编号作 ref，不必再取一次。

| 节点 | 内容 |
|---|---|
| analysis | 案情摘要（实体、持股、金额、日期，来自 facts.json）；handoff.md 全文；结构名字和五张表（现 `sections.py` 的 frame）；判断点及两种答案下的第一名；第一名结构的每一跳、适用规则和 cite_ids；这些 cite_ids 对应条文的单元原文（每条截到单元上限）；待补事项；文件清单 |
| review_draft / review_final | 同上的摘要部分，加本轮草稿里所有数字的出处核对结果（§10 `cite_check`） |
| review_intake | 事实键清单、出处清单、单据解析状态（哪些页有文本层、哪些是 OCR）、变更差异 |
| front | 已上传单据的解析摘要（每份：页数、是否扫描、识别到的表格数）、事实键清单 |
| polish | 不发包；只读草稿和出处表 |

## 10. 工具接口

服务名 `tax-read-<身份>`，四个身份各一个进程，和 tax-case-<身份> 一样绑定身份与路径权限；权限规则与 `guard_hook.py` 共用一个模块（`agent/tools/access.py`），不再两处维护：不读别的 agent 的笔记、不读早先 run 的产物和报告（改版例外按编排规范 §9）、不读 log/。

| 工具 | 参数 → 返回 |
|---|---|
| `map` | case_id → 本身份可读的目录和文件：路径、大小、一句说明（程序写死的说明表）、当前 run_id、产物摘要（结构数、分支数、判断点数）。替代 Glob |
| `search` | queries[]（或 query）, scope ∈ {law, products, case, all}, filters {jur, as_of, run_id, cand, branch, point, doc, lang, slot}, k = 8, max_chars → 每个查询的命中列表：id、scope、type、标题 / 标签、原文片段或卡片、名次、通道、有效期、语言、other_lang、parent；外加 tried、relaxed、not_found |
| `get` | id, offset, max_chars → 整条记录或整条条文，逐字；带 total_chars |
| `expand` | id, kinds[], depth ≤ 2, k → 邻居卡片，按边类型分组 |
| `ground` | id, quote → match ∈ {exact, approximate, none}，匹配到的原文区间；单据允许 approximate |
| `list` | kind, filters, k, cursor → 一类记录的卡片：法规库的 params / absences / treaties / jurisdictions / blocked / decisions / docs；产物的 structures / branches / hops / points / scenarios / open_items / requirements / transfers / exposures / penalties / past_payments；案卷的 facts / sources / dialogue / documents / pages / cells。替代各层的切片工具（§5.3） |
| `pack` | case_id, node → 预取包的路径和条目编号清单（通常由编排器调用，agent 也可重取） |
| `cite_check` | case_id, run_id → 草稿出处表的每个 ref 是否可解析、正文里的每个数字和引文是否出现在所引片段里、未被任何出处覆盖的数字清单。供 `report_check` 和复核调用 |

约定：返回里的 text、quote 逐字；不含分数；每次调用记入 `cases/_log/read.jsonl`（查询、过滤、返回编号、字符数、耗时），供评测集采集。

`search` 的 scope 为 all 时，结果按材料分组返回（法规、产物、案卷各取前几条，各自在本材料内排序），不合成一个排名：三种材料的排序没有共同的尺度，2026-11-03 试过让重排模型给并集统一排序，对产物和案卷不公平（例如问 HSBC 到账，排第一的是一条协定条款）。要某一种材料的更多结果，用该 scope 单独查。

## 11. 与四个 agent 的衔接

- **分析**：先读预取包，缺什么再 `search`；条文从结构的依据记录引用，规则层已经核对过对应关系，只有逐字引用时才再取原文；任务里列出本轮底稿已有的条目，只追加不通读；规则层的 requirements 默认返回摘要；一次 `search` 多个问题；出处表的 ref 写编号；不用 Glob 找路径，用 `map`。提示词相应改写，去掉"先读 brief.json 的各节"一类会导致整份读入的指令。
- **复核**：核数字先跑 `cite_check`，只对它报出的未覆盖数字和不匹配引文逐条看；引文用 `ground`。
- **前台**：单据上传后看 `map` 的解析状态；抽取事实时可用 `search(scope=case)` 在单据页和单元格里找；引文落地用 `ground`。多模态阅读页面图像照旧可用。
- **润色**：不变。
- **report_check**：加 `cite_check`；泄漏模式加编号格式（`\d{8}-[0-9a-f]{8}:\w+:`、`:unit:`、`#\w+` 形式的 cite_id 已在模式里）。
- **编排器**：run 结束后建产物索引；节点开始前生成预取包；任务文本内联文件清单。

## 12. 评测

按 `目标.md` 的精神：方法的采用以本项目的数字为准。测试只在用户指示时跑。

### 12.1 金标准

| 集 | 查询 | 金标 | 规模 |

### 12.2 指标

- 检索：Recall@5 / 10 / 20、nDCG@10、MRR，按语言和集分报。
- 落地：引文逐字命中率；`cite_check` 报出的未覆盖数字数。
- 端到端：分析节点的工具调用次数、读入字符数、输出 token、耗时；复核结论和退回项数。改造前的基线就是 §0 的数字。

### 12.3 消融与采用门槛

每个组件单独开关：header 上下文、稠密通道、语言均衡、图扩展、重排序、晚切分、稀疏权重（模型写的说明待全库到位后再加；不做模型对比，2026-11-03 用户定）。采用条件：在开发集上 nDCG@10 或 Recall@10 有提升，且在测试集上不下降；重排序还要满足单次延迟在 GPU 上低于 1 秒。结果记在 `agent/retrieval_eval.md`（英文）。
