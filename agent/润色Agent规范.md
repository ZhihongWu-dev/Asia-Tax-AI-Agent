# 润色 Agent 规范（最小集）

2026-11-01。四个 Agent 之一（前台、分析、润色、复核）。本文只定它的职责、输入输出、底稿和递交给它的 prompt。

**语言**：本规范用中文，供人阅读；英文副本 `agent/polish_agent_spec.en.md`，两者不一致时以中文版为准，改中文版时同步改英文副本。AI 写进文件的一切自写文字用英文——代码、注释、prompt（系统实际递交的是英文副本里的那段）、底稿、bug；润色后的报告跟客户语言（默认英文）；引文原样。

**轮的定义**见前台规范开头：一轮一个 run_id。润色 Agent 第 N 轮只读本轮的草稿，不读旧轮；底稿按 round-N 分目录、不跨轮。

## 1. 定位

**系统一句话**：客户（公司或个人）在中国大陆、香港、新加坡、日本、泰国之间持股收取股息或为此转让股权；系统比较不同持股结构和付款路径在两侧的税负，找出税负最低且法律条件能满足的结构，说明现状哪里有问题、可以怎么改。库里只有这五地的所得税类法规。

润色 Agent 在复核通过草稿之后工作，出稿后由复核比对成稿和草稿。分析写的是完整草稿，论证齐全但偏长；润色把它改成一份可以直接交给客户的书面意见，附录之前的正文 5 到 10 页，附录另计。草稿原样保留，详细论证留在草稿里。

**可以删，不能改。** 成稿比草稿短是设计如此。删掉的内容不算错；数字、事实、假设、所依据的结构和法律结论被改动才算错，也不能新增论断。

## 2. 输入

`cases/<case_id>/report/<run_id>/briefing.md`、`briefing.sources.json`，以及 `cases/<case_id>/intake/handoff.md`。本轮状态应为 `reviewed`，即草稿已通过复核（`review.md` 末句 `POLISHABLE`），在此之前服务拒绝写入成稿。不读产物，不读任何人的底稿。

## 3. 输出

- `briefing.polished.md`：客户成稿。
- `briefing.polished.sources.json`：只提交保留下来的条目，每条写 `id` 和 `where`（`<部分> | <成稿原句片段>`，片段逐字取自成稿，中间可用 … 省略）。`claim`、`kind`、`ref` 由服务从草稿复制，润色不能新增条目。
- `briefing.pdf`：调 `render_pdf` 生成。版式由模板决定。

## 4. 成稿要求

**语体**：正式书面语，读起来是事务所的意见书，不是说明文或对话。不用"一句话、为什么、省多少、花多少、靠什么、怎么做"这类口语标签，改用"建议摘要、选择理由、预期节税、实施成本、成立前提、实施步骤"这类措辞。不出现系统标识和系统自用语（候选或分支编号、run_id、字段名、工具名、上下限、规则工具、模型、优化层、规则层、法规库、产物），也不说明税负是哪个工具算出来的、备选方案是怎么枚举出来的。草稿末尾的内部编号行不进成稿。不写过程性说明：贵方被问过什么、比较时如何取值、哪些条文尚未收录之类都不写，假设直接陈述为本意见的前提，拿不到原文的结论写成建议当地顾问确认。

**篇幅**：附录之前的正文 5 到 10 页，附录另计。篇幅跟着内容走，不为页数删减或凑字。模板每页约一千七百字。保留结论、关键数字、依据条款和让客户看懂所需的论证。表格单元格写短语，不写句子。

**结构**：保留一到七节和附录 A、B 的标题。前提部分是一小段话，不用列表，不超过五句，每句不超过四十词，写明假设并指向附录 A，这样流程图能留在第 1 页。第七节和附录 A 的问题不重复：一处写完整问法和结果，另一处只引编号。备选方案的编号不留空号，删掉的方案用一句话交代。

**必须留下**：推荐结构及其理由、现状的问题、两侧税负和节税金额、一次性成本、成立条件、单据之间的矛盾，以及每个会改变设计的待确认问题和答案不同时的结果。

**流程图**：放在第一节，写成标记为 flow 的代码块，内容是 JSON，格式见 `agent/templates/flowchart.example.json`。只填结构、持股比例、调整动作和税负结果，图由模板画。图上方不加标题，不写字符画。

**实质问题只报不修**：论证有漏洞、条文用错、数字矛盾、假设不全，写进 `issues` 底稿并在交回摘要里说明，不出 PDF，退回分析。

**复核退回时**：只处理措辞、删减和版面方面的意见。需要新增内容或改动数字、结论的意见属于分析，写进 `issues`，不自己补。

## 5. 底稿（三本）

目录 `cases/<case_id>/notes/polish/round-N/`，只追加不改；条目头 `### <本子>-<序号> | 日期 | round N.k | run_id`。底稿不是出处，不给客户。

| 本子 | 写什么 |
|---|---|
| `plan` | 动笔前的取舍：哪些留、哪些删、每页放什么 |
| `changes` | 删了什么、并了什么，为什么不影响结论 |
| `issues` | 实质问题，退回分析 |

## 6. 工具与权限

读草稿、出处表、handoff 和流程图范例用宿主 Read；核对法规全称用 `tax-db`。写经 `tax-case-polish`：`write_polished`、`edit_polished`、`render_pdf`、`notes_append`、`bug_append`、`report_check`。润色不读 PDF 和图片（2026-11-03 前所用的 qwen3.7-max 不收图片），守卫会拒绝；版面靠 `render_pdf` 返回的页数、各节和流程图所在页、每页填充比例判断。

## 7. 自检

反复调 `render_pdf` 和 `report_check`（target=polished），直到 `latex_errors` 和 `overfull` 为 0、`problems` 为空。`body_pages` 是附录之前的页数，在 5 到 10 之间即可，不必为页数继续删改。`flow_page` 应是第 1 页；`page_fill` 里某个中间页明显偏低，说明图或表被挤到了下一页，缩短它前面的文字。`numbers_omitted` 和 `sources_cut` 列的是被删内容，逐项确认没有删掉上面"必须留下"的东西。

## 8. 不做

不改实质，不新增论断或出处，不与客户对话，不读产物和别人的底稿，不改模板。

## 9. Bug 反馈

运行中撞到系统自己的毛病，用 `bug_append` 记到 `cases/<case_id>/bugs/polish.md`，只报不修。草稿的实质问题进 `issues`，不是 bug。
