# 分析 Agent 规范（最小集）

2026-10-31。四个 Agent 之一（前台、分析、润色、复核）。本文只定它的职责、输入输出、报告结构和递交给它的 prompt。

**语言**：本规范用中文，供人阅读；英文副本 `agent/analysis_agent_spec.en.md`，两者不一致时以中文版为准，改中文版时同步改英文副本。AI 写进文件的一切自写文字用英文——代码、注释、工具说明、prompt（系统实际递交的是英文副本里的那段）、底稿、核对单、handoff、bug 反馈、日志、产物字段；原件、条文、引文、客户原话保持原文，不翻译。唯一例外是给客户看的文字（对客户的回话、briefing）跟客户的语言。核对单的总判断用英文记号：交接包 `RUNNABLE` / `REVISE`，草稿 `DELIVERABLE` / `REVISE`（2026-11-06 起没有成稿阶段）。

**轮的定义**见前台规范开头：一轮一个 run_id；修订 N.k 不换 run_id；上下文和底稿不跨轮。分析 Agent 第 N 轮不读旧轮的 `report/` 和旧 run 的产物，上一轮与本轮的差别只从 handoff.md 和 diff.json 读。

## 1. 定位

**系统一句话**：客户（公司或个人）在中国大陆、香港、新加坡、日本、泰国、越南、马来西亚、阿联酋、印尼、印度、韩国之间持股收取股息或为此转让股权；系统比较不同持股结构和付款路径在两侧的税负，找出税负最低且法律条件能满足的结构，说明现状哪里有问题、可以怎么改。库里只有这些地区的所得税类法规。

分析 Agent 管输出端，直接写交给客户的报告（2026-11-06 起没有润色环节：复核通过后，程序组出客户副本——抬头和日期、表格、流程图、附录 B——再排版出 PDF 交付）。分析的对象是跨境股息的持股结构与付款路径的税负优化：读前台的交接包和优化层产物，弄清最优结构为什么是它、税怎么来、成立要什么条件，在这个结构之上制定方案，写导师要的 recommendation briefing。优化层给的是结构（税负最低且条件能满足的持股结构和付款路径），不是方案；加上怎么从现状走过去、要满足什么、先后顺序、代价、前提、被否定时怎么办，才是方案，这是分析 Agent 的活。它不与客户对话，不抽事实，不改任何产物或库表。

上下文原则：常驻上下文只装交接包（facts、sources、answers、notes、constraints、handoff）和产物的 JSON；原始单据、法条全文、网页都按需用工具取，取完不留。权限不限，限的是默认装载量。

## 2. 输入

`cases/<case_id>/intake/`（见前台规范 §3）。前提：`intake/review_intake.md` 存在且末句为"可跑"；没有或为"需改"就不写报告，只在 `report/<run_id>/` 留一行说明退回前台。`handoff.md` 先读；然后 `products/<run_id>/` 的 ranking、deltas、open_items、paths、tax、requirements/、transfers/、exposure（在 deltas 里）、version；需要追数时读 hops/、edges/ 和规则层 trace。

## 3. 输出

`cases/<case_id>/report/<run_id>/briefing.md`（草稿；客户语言，默认英文）加 `briefing.sources.json`（出处表，不进报告正文）。这就是交给客户的成稿（2026-11-06 起没有润色环节）：数字、结构、法律结论要对，文字也要达到意见书的标准，没有人再改写。Agent 只写各部分的正文；写完状态变 `drafted`，复核接手。

**交给模板和程序，不写进提示词（2026-11-12）**：模板或程序固定下来的，一律不向 Agent 描述，只有按部分的词数上限例外（见下）。编排的排版步骤从草稿组出客户副本（`agent/tools/report_form.py`）：顶上的标题和日期（facts.json 的 instructed_on），第 1 部分末尾的流程图（按产物生成，`frame/blocks/flow.json`），第 5 部分标题下的税负表，附录 A 标题下的假设表和末尾的事实缺口，按引用标记和出处表生成的附录 B，引用标记只印显示文字，带案卷号或 run_id 的行一律不出现；再由 `render_pdf`（只归程序）排版，字号和版式在模板里定。Agent 不再调 `render_pdf`，报告也没有页数下限和上限。

**按部分设词数上限（2026-11-12）**：每部分一个上限，基数加每项额度（第 3 部分按结构个数、附录 A 按假设个数），写在 Agent 读不到的 `agent/tools/report_limits.json`。引用标记、引号里的逐字引文、表格、代码块、程序标记和标题不计数；一个中日韩字符算半个词。框架在 "Word limits" 下写明每部分的上限，让每部分从初稿起就写在上限内（2026-11-12 用户定：这是"模板的事不告诉 Agent"唯一的例外；此前初稿常超出二到四倍，删字约占写作时间的三分之一）。`part_check` 和 `report_check`（target=draft）在某部分超限时报一句 "Part N: X words, limit Y. Cut it."。每次检查把各部分词数写进 `cases/<case_id>/log/word_counts.jsonl`，供校准。全篇不设总上限。

**读者是客户，结构是导师定的。** 报告是一份筹划建议书，按顶级事务所给客户的书面意见的标准写：客户没有系统的上下文，不知道也不该知道候选、分支、槽位、上下限；结构、路径、实体用客户自己的名称（"深圳晨光 → 新加坡母公司直接持股"），数字直接写（人民币 1,400 万元、税负 5%），术语第一次出现用一句话解释，正文不出现任何系统标识（候选编号、分支编号、run_id、字段名、工具名）。

**报告结构**

| 部分 | 回答客户的什么问题 |
|---|---|
| 起首 | 声明本报告采用的假设，详见附录 A（在第 1 部分之前；上面的标题和日期归模板） |
| 一、策略思路（Strategy） | 摘要，按固定顺序写（2026-11-12）：客户要什么，包括方案取决于的集团自己的选择（框架的"The group's own choices"；客户没说的那项两种都写，因为它是集团的决定，不是假设）；这一笔怎么付；以后各笔怎么付、先做什么（框架的"This dividend and later dividends"）；值多少：每次分红比基准（现有链条把钱付到客户要的终点）省多少、一次性成本和几次回本；靠什么成立、集团做什么让它更稳。根据客户现有资源（实体、持股、人员与场所、历史分红与已缴税）和优化结果制定。流程图由程序加在这一部分末尾（现状结构 → 调整动作 → 目标结构 → 分红路径）；方案取决于某个选择或先后顺序时，程序再加一张这一笔与以后各笔的表 |
| 二、现状（Current State） | 现在的结构是什么，这笔款项按现状要交多少税，现状哪里有问题、每处带数字（框架的"What is wrong with the position as it stands"：钱到不了终点、压在未确认判断点上的税、数字所依赖的动作、历史已缴税的追回空间和补税风险） |
| 三、备选方案（Alternatives） | 考虑过哪些可行结构，在同一组有利假设下各交多少税、要不要重组、一次性成本、几次回本；只详写现状、第一名和每次省得同样多的结构，其余各一句；被占优的、不回本的说明为什么排除。不写某个假设落空时会怎样 |
| 四、最优方案（Optimal） | 为什么设计建立在这个结构上：为什么它排第一（税最低；税相同时回本最快）、成立的前提（写附录 A 的编号，不在这里重复论证）；数字在第一、五部分 |
| 五、税负比较（Tax Comparison） | 程序的税负表（每个结构每一步的税、这笔股息的税、每次比基准省多少、一次性成本、回本次数，都是有利假设下的一个数）和"数字靠什么"表（钱汇入终点所在法域时的税、判断点全部不利时的税）在标题下；Agent 写一段说明这些数从哪来，不重抄表里的数 |
| 六、条件与要求（Requirements） | 用编号列表写最优方案成立要满足的条件：事实已经满足的（各附条款）、要交的文件、期限、证明年度。取决于判断的条件不在这里论证，只写"见附录 A 第 n 项" |
| 七、执行（Implementation） | 用编号列表写从现状到最优的各步动作、每步的程序与期限。第一步是付款前把要确认的判断点拿去问能回答的人（如主管税务机关、律师），并说明税局的咨询答复没有约束力；要申报的待遇写出申报时机的选择（如付款时按协定税率申报，或先按法定税率扣缴、事后申请退税）及各自的后果；顺序要保住已有的待遇（某一步会让一条路径失效时，先做依赖那条路径的事）；方案自己的某一步本身就是所依赖判断点的不利因素时（如在受益所有人的观察期内把股息转付出去），把它排到观察期之外，或写明在期内做要让那一点付出什么。档案里对某个判断点不利、集团又能改的事实（框架的"Facts on file for each point"里标 against 的）写成付款前加固这一点的步骤；这一笔和为以后各笔做的重组，按框架"This dividend and later dividends"给的先后排。客户带回结果后新开一轮重算，报告不预写被否定后的设计 |
| 附录 A 待确认事项与假设 | 程序的假设表在标题下；Agent 逐项写一段：本报告取的答案、依据条款、档案里对它不利的事实（照条文逐项对照，不粉饰）、谁来确认、怎么确认；客户已经提供的事实不再作为问题。同一个有利答案有几条成立路径时（如收款人自己按因素认定受益所有人，和经由本身符合条件的持股人的安全港，见 judgment_points 的安全港），逐条写出，按档案事实的强弱排序，最强的一条作为向税局陈述的主论点，其余并列为另外的论点，不写成被否定后才用的退路。事后被否会补税的那一项写一句后果（补税加滞纳金，取产物的 exposure_if_denied）。客户还能补的事实由程序列在末尾 |
| 附录 B 法规依据与资料来源 | 归程序：正文引用过的每条条文（取自引用标记）、官方指引、客户单据，分三层标注：库里已验收 / 官方网站原文 / 二手资料。Agent 不写 |

**集团自己的选择不是假设（2026-11-12）**：钱是否必须汇入终点所在法域、这一笔能否等、是否已经决议付给现在的收款人，这些由客户决定，不是税局回答的判断点。客户说了的，是方案的事实；客户没说、而第一名结构随之改变的，第一部分两种都写（程序的选择表），附录 A 把它列为集团要做的决定，两种情形的数字都写进报告。框架的"Figures the report must state"列出需要的数字，`report_check` 会报出缺的那个。

**假设的写法**：全篇按有利假设讨论——不确定的判断点取对方案有利的一侧展开论证，像顾问写意见书那样，在正文起首一次性声明"以下分析假设……，这些点待贵司确认，详见附录 A"；正文只写有利假设下的一个数，不写"有利到不利"的区间，也不写某个假设落空时设计变成什么：客户带回不利的结果时新开一轮重算（目标.md §4.2 第 6 条）。正文不逐句标注，不写"本方案假设……"这类声明。

**引用方式（2026-11-12）**：像一份专业意见书，在行文中依据某条的地方写出条文名；每处引用写成标记 `{{cite:<cite_id>|<显示文字>}}`，显示文字是客户读到的条文名称（`{{cite:cn.sta.2019-35#10|Article 10 of the Administrative Measures}}`），便于精确核对出处。客户副本只显示显示文字，条文由程序列进附录 B。`report_check` / `part_check` 会退回库里没有的 cite_id，和写成句子而不是名称的显示文字。正文不放脚注编号、不放文件路径。

**`briefing.sources.json`**（给复核的出处表，客户不看）：正文每个数字一条，取自客户单据的每个事实一条 kind 为 document、ref 写单据与页：`{id, where（部分 + 原句片段）, claim, kind: product | tool | url | document | name, ref（产物记录编号 / 工具命令 / URL + 日期 / 单据与页）, note}`。用标记引用的条文不必登记：程序按每个标记补一条 `cite` 行（`cite_check`、`reasons.py`）。复核靠它对数。

## 5. 守则（只约束交付物，不约束过程）

1. **为客户而写**：不出现系统标识和内部术语；结构用实体名称；术语首次出现解释一句；像人写的意见书，不像流程输出。
2. **数来自产物和工具**：不自己做税额算术；每个数取有利假设下的一个值（产物分支的 floor）；只有未知事实本身造成的范围才写范围，并说明取决于哪个事实；一次性成本只写调整动作直接触发、当时就要缴的税，取决于税局裁量的部分写成附录 A 的假设，不写成成本区间。结构的数字可能取决于集团要做的事（框架里"what it asks the group to do"列的动作，例如股息不汇入某地）：税额表下的说明给出不照做时的税；报告写出这一步、这笔代价和分支记录里的理由，不另编理由（不汇入的条件不是免税）。
3. **假设与事实分开**：全篇按最优假设讨论，假设在起首一次性声明并进附录 A，正文不逐句标注；客户确认过的才写成事实（handoff 里说明了哪些已确认），没有把假设写成客户已确认的事实；单据矛盾如实列出，不选边。
4. **法律论证成立**：每个待遇都引到条款，并说明本案怎么满足、哪里不满足或不确定；引用像专业意见书，出处进附录 B 和 sources.json。来源分三层：库里已验收的条文 / 官方网站原文 / 二手资料（只作线索，正文用到要说明）。
5. **未决项不略过**：最优方案依赖的每个判断点都进附录 A（程序假设表的每一行），写清档案里对它有利和不利的事实；会改变结论的事实缺口（gaps_list）补不上的，写明缺什么。
6. **核实的边界**：能写交叉核对发现的矛盾，不能写"属实"；不打分、不估概率；某项假设偏弱时，用条文逐项对照的事实说明，不用可能性说。
7. **方案建立在优化层的结构上**：方案所依据的结构就是优化层排第一的（每次的税最低，税相同时回本次数最少），不另选结构；结构之上的动作、顺序、前提、代价由分析 Agent 制定，这部分才是方案。
8. **比较只在有利假设下做**："最低""唯一""相同"这类话只对应程序税负表（有利假设）里的数；不用不利情景比较结构；不写内部名次。
9. **措辞也是交付物**（2026-11-06 起没有润色环节，这份报告不经改写交给客户）：正式书面语，不用"一句话、为什么、省多少"这类口语标签；不出现优化层用语（per 100、modelled、variant、judgment world、ranked N-th、the library）；第六、七部分用编号列表。版面、抬头、表格、流程图和附录 B 归模板和程序（§3）。

（2026-11-12 删去：预判守则；"每件事全篇只论证一次"——按部分的词数上限会做这件事；句子 55 词上限；正文 5 到 10 页。）

## 6. 不做

不与客户对话；不改 facts / answers / 产物 / 库；不补值；不替库改数（发现缺漏写 `to_collect.md`）；不写没有出处的数；不读 `notes/front/`、`notes/review/`、自己的旧轮目录、旧轮报告、旧 run 产物；不把底稿当出处。

## 6a. Bug 反馈

正常运行中会撞到系统自己的毛病：工具报错或输出不合规范、产物内部对不上、库里条文与官方原文不符、参数值过期、链接失效、规范两处说法矛盾。这些不是本案的事实，也不归复核管，归开发者。每个 Agent 只写自己的一份：`cases/<case_id>/bugs/analysis.md`，只追加。

一条一个 bug：`### B-<序号> | 日期 | round N.k`，正文五项——层（数据库 / 规则层 / 优化层 / 工具 / 联网源 / 规范）、现象（命令或操作 + 实际输出，原样贴）、期望（规范或原文说应该是什么）、复现步骤、本轮怎么绕过的（绕不过就写"阻塞"）。

规则：只报不修——不改库、不改工具、不改规范；缺陷可能改变报告里的数字或排名时，`bug_append` 传 `affects_result=true`：运行停下等修复，不要绕过它写报告。绕过的办法若影响报告里的数或结论，要在报告的假设清单（分析）或核对单（复核）或 handoff（前台）里注明。库里缺一份法规是采集需求，走 `to_collect.md`，不是 bug；另一个 Agent 的交付物有错是复核的事，也不是 bug；程序发回的修改要求（检查返回的问题、宿主要求重写的消息）也不是 bug。这份文件对 Agent 只写不读（2026-11-12）：Agent 不读它；重复的（同层、同现象）由 `bug_append` 自己并到原条下，记一行"recurrence round N"，只回一句话。它跨轮保留，因为它记的是系统不是案子。

## 7. 自检（交给复核前）

- 一到七节、附录 A 齐全；起首的假设声明齐全。
- 正文没有系统标识；术语第一次出现有解释。
- 方案所依据的结构 = ranking 第一行（同一 run_id）；两侧税额与产物一致。
- `briefing.sources.json` 覆盖正文每个数字和取自单据的事实，每条有 where 和 ref；条文都用引用标记。
- 起首的假设声明和附录 A 的假设清单 = answers 里 unknown 而报告取了值的键；会翻转设计的未决项全部出现在第七节和附录 A。
- `flags.md` 每条都落进了附录 A 或已在底稿里写明查清。
- `report_check`（target=draft）的 problems 为空。
