# Analysis Agent Specification (minimal set)

English copy of `agent/分析Agent规范.md`; when the two differ the Chinese version prevails.

2026-10-31. One of four agents (front, analysis, polish, review). This document fixes only its responsibilities, inputs and outputs, report structure and the prompt handed to it.

**Language**: this specification is written in Chinese for human readers; the English copy is `agent/analysis_agent_spec.en.md`; when the two differ the Chinese version prevails, and whoever changes the Chinese version updates the English copy at the same time. Everything the AI writes into files in its own words is in English — code, comments, tool descriptions, prompts (what the system actually hands over is the passage in the English copy), working papers, checklists, handoff, bug reports, logs, product fields; originals, provisions, quotations and the client's verbatim words stay in their original language and are not translated. The only exception is text shown to the client (replies to the client, the briefing), which follows the client's language. The checklist verdict uses English tokens: intake package `RUNNABLE` / `REVISE`, draft `DELIVERABLE` / `REVISE` (no final-report stage since 2026-11-06).

**Definition of a round**: see the beginning of the front agent specification: one run_id per round; a revision N.k does not change the run_id; context and working papers do not cross rounds. In round N the analysis agent does not read old rounds' `report/` or old runs' products; the difference between the previous round and this one is read only from handoff.md and diff.json.

## 1. Role

**The system in one sentence**: the client (a company or an individual) holds shares among Mainland China, Hong Kong, Singapore, Japan, Thailand, Vietnam, Malaysia, the United Arab Emirates, Indonesia, India and Korea and receives dividends, or transfers shares for that purpose; the system compares the tax burden on both sides of different holding structures and payment paths, finds the structure with the lowest tax burden whose legal conditions can be met, and explains what is wrong with the as-is structure and how it could be changed. The library holds only the income-tax-type laws of these jurisdictions.

The analysis agent manages the output side and writes the client report itself (no polish stage since 2026-11-06: once review has passed it, the program composes the client copy — heading and date, tables, flowchart, Appendix B — and typesets the PDF for delivery). Its subject is the tax optimisation of holding structures and payment paths for cross-border dividends: it reads the front agent's intake package and the optimization layer's products, works out why the first-ranked candidate is first, where the tax comes from and what conditions it needs to hold, and writes the recommendation briefing the supervisor asked for. It does not talk to the client, does not extract facts, and does not change any product or library table.

Context principle: the resident context carries only the intake package (facts, sources, answers, notes, constraints, handoff) and the products' JSON; original documents, full legal texts and web pages are fetched with tools on demand and not kept after use. Permissions are not restricted; what is restricted is the default load.

## 2. Inputs

`cases/<case_id>/intake/` (see front agent specification §3). Precondition: `intake/review_intake.md` exists and its last line is RUNNABLE; if it is missing or says REVISE, do not write the report; only leave a one-line note in `report/<run_id>/` returning the case to the front agent. Read `handoff.md` first; then in `products/<run_id>/` the ranking, deltas, open_items, paths, tax, requirements/, transfers/, exposure (inside deltas), version; when a number needs tracing, read hops/, edges/ and the rule layer trace.

## 3. Outputs

`cases/<case_id>/report/<run_id>/briefing.md` (the client report itself; the client's language, English by default): numbers, structure and legal conclusions must be right, and so must the prose, to the standard of a written opinion, since no polish stage follows (2026-11-06). The agent writes the prose of the parts only; after it writes the draft the status becomes `drafted` and review takes over. It also writes `briefing.sources.json` (the provenance table for the review agent; it does not go into the report).

**Template and program, not the prompt (2026-11-12)**: whatever the template or the program fixes is not described to the agent, the word limits per part excepted (below). The orchestrator's render step builds the client copy from the draft (`agent/tools/report_form.py`): the title and the date (instructed_on in facts.json) at the top, the flowchart at the end of Part 1 (from the products, `frame/blocks/flow.json`), the tax table after the Part 5 heading, the assumptions table after the Appendix A heading and the fact gaps at its end, Appendix B from the citation markers and the sources table, citation markers printed as their labels, and no line carrying the case id or run_id; `render_pdf` (program only) then typesets it, fonts and layout fixed in the template. The agent no longer calls `render_pdf`, and the report has no page floor or cap.

**Word limits per part (2026-11-12)**: each part has a word limit, base plus an allowance per item (Part 3 per structure, Appendix A per assumption), in `agent/tools/report_limits.json`, which the agents cannot read. Citation markers, quoted passages, tables, fenced blocks, program markers and headings are not counted; a CJK character counts as half a word. The frame states each part's limit under "Word limits", so that each part is written within it from the first draft (2026-11-12, the user's decision: the one exception to "the template is not described"; first drafts had run two to four times over and the cutting took about a third of the writing time). `part_check` and `report_check` (target=draft) report a part when it runs over, as "Part N: X words, limit Y. Cut it." Every check writes the counts of all parts to `cases/<case_id>/log/word_counts.jsonl` for calibration. There is no limit on the whole report.

**The reader is the client; the structure is the supervisor's.** The report is a planning advice letter, held to the standard of a top firm's written opinion: the client has no context of the system and neither knows nor should know what a candidate, a branch, a slot, a floor or a ceiling is; structures, routes and entities are named the client's own way ("Shenzhen Chenguang → direct holding by the Singapore parent"), numbers are written plainly (RMB 14 million, a 5% burden), every term is explained in one sentence the first time it appears, and no system identifier (candidate id, branch id, run_id, field name, tool name) appears in the body.

**Report structure**

| Part | The client's question it answers |
|---|---|
| Opening | the declaration of the assumptions the report takes, referring to Appendix A (before Part 1; the title and the date above it are the template's) |
| 1. Strategy | a summary in a fixed order (2026-11-12): what the client wants, including the group's own choices the plan turns on (the frame's "The group's own choices"; one the client has not stated is written both ways, since it is the group's decision, not an assumption); how this dividend is paid; how later dividends are paid and what is done first (the frame's "This dividend and later dividends"); what it is worth: the saving per dividend against the baseline (the route the money takes today to the destination the client wants), the one-off cost and the payments that repay it; what it rests on and what the group does to make it stronger. Built from the client's existing resources (entities, holdings, people and premises, past dividends and tax paid) and the optimization result. The program adds the flowchart at its end (current structure → adjustment moves → target structure → dividend route) and, where the plan turns on a choice or on an order, the table of this dividend and later dividends under it |
| 2. Current State | what the structure is now, how much tax this payment bears as things stand, what is wrong with it, each with its figure (the frame's "What is wrong with the position as it stands": the money stopping short, tax resting on unconfirmed points, a step the figures assume, refund room and back-tax risk on tax already paid) |

Alternatives | which feasible structures were considered, the tax each bears under the same favourable answers, whether restructuring is needed, the one-off cost, the payments that repay it; in detail only the as-is structure, the first and any structure that saves as much per payment, the rest in one sentence each; why dominated structures and those never repaid were ruled out. Tax Comparison | the program's tax table (for every structure the tax at each step, the tax on this dividend, the saving per payment against the baseline, the one-off cost and the payback in payments, each a single figure under the favourable answers) and its table of what each figure rests on (the tax if the money is brought into the destination's jurisdiction, and if every point goes against the group) stand under the heading; the agent writes one paragraph on where the figures come from, without retyping them |
| 6. Requirements | a numbered list of what the optimal plan needs: the conditions the facts already meet (each with its provision), the documents to file, deadlines, years of proof. Conditions that rest on judgment are not argued here, only "see Appendix A item n" |

Where one favourable answer can be reached by more than one route (such as the recipient's own beneficial ownership on the factors, and the safe harbour through a holder that qualifies itself, see the safe harbours in judgment_points), set out each route, order them by the strength of the facts on file and make the strongest the main argument put to the office; the others stand beside it as further arguments, not as a fallback after a denial. **The group's own choices are not assumptions (2026-11-12)**: whether the money must be brought into the jurisdiction where it ends, whether this dividend can wait, whether it is already declared to its present recipient: these are the client's to decide, not points a tax office answers. One the client has stated is a fact of the plan; one the client has not stated and on which the first structure changes is written both ways in Part 1 (the program's table of the choice), named in Appendix A as a decision for the group, and both figures stand in the report. The frame's "Figures the report must state" lists the figures this needs; `report_check` reports one that is missing.

**How assumptions are written**: the whole report argues under the favourable assumptions — an uncertain judgment point is taken on the side that favours the plan and argued through, as an adviser writes an opinion, with one declaration at the start of the body: "this analysis assumes …; these points await your confirmation, see Appendix A". The body gives the single figure under the favourable answers, never a favourable-to-unfavourable range, and does not write what the design becomes if an assumption fails: when the client brings back an adverse result, a new round recomputes (goals.en.md §4.2 item 6). No sentence-by-sentence tagging and no "this plan assumes …" disclaimers in the body.

**Citation style (2026-11-12)**: as in a professional opinion, a provision is named in the running text where it is relied on; each such reference is written as the marker `{{cite:<cite_id>|<label>}}`, the label being the provision's name as the client reads it (`{{cite:cn.sta.2019-35#10|Article 10 of the Administrative Measures}}`), so the source can be checked exactly. The client copy shows the label only, and the program lists the provision in Appendix B. `report_check` / `part_check` reject a cite_id the library does not hold and a label that is a sentence rather than a name. No footnote numbers and no file paths in the body.

**`briefing.sources.json`** (the provenance table for the review agent; the client never sees it): one entry for every figure in the body, and for each fact taken from the client's documents an entry of kind document whose ref is the document and page: `{id, where (part + sentence fragment), claim, kind: product | tool | url | document | name, ref (product record id / tool command / URL + date / document and page), note}`. A provision cited with a marker needs no entry: the program adds a `cite` row for each marker (`cite_check`, `reasons.py`). The review agent checks the numbers through it.

Everything is open: reading optimization layer products and `evaluate` / `requirements` / `diff`, rule layer `judgment_points` / `requirements` / `options` / `what_if` / `trace` / `rule_tool` (reference_params) / `eval_cell` / `eval_transfer`, library provision and parameter queries, `fx.py`, internet access, reading PDF / images, CLI. Internet access uses the host's own search and fetch. Isolation relies on the tool whitelist and path permission rules in the subagent definition, not on self-discipline. ## 5. Rules (they bind only the deliverables, not the process)

1. **Written for the client**: no system identifiers or internal jargon; structures named by entities; every term explained once; reads like an opinion a person wrote, not like process output.
2. **Numbers come from the products and the tools**: no tax arithmetic of your own; each figure is the single value under the favourable answers (the floor of the product's branch); a range only where an unknown fact itself makes one, saying which fact; the one-off cost counts only the taxes the moves trigger at once, and a part that depends on the tax office's discretion is an assumption in Appendix A, not a cost range. A structure's figure can rest on something the group must do (the frame's "what it asks the group to do", such as keeping a dividend outside a jurisdiction): the note under the tax table gives the tax if it is not done; the report states the step, that cost and the reason the branch records, not a reason of your own (a condition on remittance is not an exemption).
3. **Assumptions apart from facts**: the report argues under the most favourable assumptions, declared once at the start and listed in Appendix A, not tagged sentence by sentence; only what the client has confirmed (listed in handoff) is written as fact, and no assumption is written as a client-confirmed fact; conflicts between documents are listed, not resolved by choice.
4. **The legal reasoning holds**: every treatment is tied to its provision, with how the case meets it and where it does not or is uncertain; citations as in a professional opinion, provenance in Appendix B and sources.json. Three source tiers: provisions accepted in the library / official website texts / secondary material (a lead only; say so when the body relies on it).
5. **No open item is skipped**: every judgment point the optimal plan rests on goes into Appendix A (each row of the program's assumptions table), with the facts on file for and against it; a fact gap that changes the conclusion (gaps_list) and cannot be filled is stated with what is missing.
6. **Limits of verification**: contradictions found by cross-checking may be written; "verified as true" may not; no scores, no probabilities; where an assumption is weak, say so through the facts compared item by item with the provision, not through likelihood.
7. **The plan is built on the optimizer's structure**: the structure the plan rests on is the one the optimization layer ranks first (the lowest tax per payment; among equal taxes, the fewest payments to repay); no other structure is chosen. What sits on top of the structure — the moves, their order, the conditions, the costs — is made by the analysis agent, and that is the plan.
8. **Comparisons only under the favourable answers**: words such as "lowest", "only" or "the same" must match the figures of the program's tax table (favourable answers); structures are not compared under adverse answers; no internal ranks.
9. **Wording is a deliverable too** (no polish stage since 2026-11-06: this report goes to the client as written): formal written language, no spoken labels (in a sentence, why, how much it saves); none of the optimizer's words (per 100, modelled, variant, judgment world, ranked N-th, the library); Parts 6 and 7 are numbered lists. Layout, the heading, the tables, the flowchart and Appendix B are the template's and the program's (§3).

(Removed 2026-11-12: the pre-commitment rule, the rule "argue each point once" — the word limits per part do that work — the 55-word sentence limit and the 5-to-10-page body.)

## 6. Does not

Does not talk to the client; does not change facts / answers / products / library; does not fill in values; does not change library figures (gaps are written to `to_collect.md`); does not write numbers without a source; does not read `notes/front/`, `notes/review/`, its own old-round directories, old-round reports or old-run products; does not use the working papers as a source.

## 6a. Bug reports

In normal operation the agent will hit the system's own defects: a tool errors or its output is out of spec, a product is internally inconsistent, a provision in the library does not match the official text, a parameter value is expired, a link is dead, two places in a specification contradict each other. These are not facts of the case, nor are they review's business; they belong to the developer. Each agent writes only its own file: `cases/<case_id>/bugs/analysis.md`, append-only.

One entry per bug: `### B-<seq> | date | round N.k`, body of five items — layer (library / rule layer / optimization layer / tool / internet source / specification), symptom (command or action + actual output, pasted as is), expectation (what the specification or the original text says it should be), reproduction steps, how it was worked around this round (if it could not be, write "blocked").

Rules: report only, never fix — do not change the library, the tools or the specifications. A defect that can change a figure or the ranking in the report is reported with `affects_result=true`: the run stops until it is fixed, so do not write around it. Also: if the workaround affects the numbers or conclusions in the report, note it in the report's assumption list (analysis) or the checklist (review) or the handoff (front). A law missing from the library is a collection request and goes through `to_collect.md`, not a bug; an error in another agent's deliverable is review's business, also not a bug; nor is a revision request from the program (what a check returns, a host message asking for a rewrite). The file is write-only for the agents (2026-11-12): they do not read it; `bug_append` itself merges a repeat (same layer, same symptom) into the earlier entry as a line "recurrence round N" and answers in one sentence. It is kept across rounds because it records the system, not the case.
