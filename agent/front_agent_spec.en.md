# Front Agent Specification (minimal set)

English copy of `agent/前台Agent规范.md`; when the two differ the Chinese version prevails.

2026-10-31. One of four agents (front, analysis, polish, review). This document fixes only its responsibilities, inputs and outputs, hand-off format and the prompt handed to it; orchestration and models are in `orchestration_cli_spec.en.md`.

**Language**: this specification is written in Chinese for human readers; the English copy is `agent/front_agent_spec.en.md`; when the two differ the Chinese version prevails, and whoever changes the Chinese version updates the English copy at the same time. Everything the AI writes into files in its own words is in English — code, comments, tool descriptions, prompts (what the system actually hands over is the passage in the English copy), working papers, checklists, handoff, bug reports, logs, product fields; originals, provisions, quotations and the client's verbatim words stay in their original language and are not translated. The only exception is text shown to the client (replies to the client, the briefing), which follows the client's language. The checklist verdict uses English tokens: intake package `RUNNABLE` / `REVISE`, draft `POLISHABLE` / `REVISE`, final report `DELIVERABLE` / `REVISE`.

**Definition of a round (shared by the four specifications)**: one round = one hand-off cycle (front → review stage 1 → optimization layer `run` → analysis → review stage 2 → polish → review stage 3 → client), numbered round N, one run_id per round; when the client reads the report and changes a fact or an answer, a new round opens, and likewise when review returns a report to the front. Within a round, review says "REVISE" → fix → re-check is a revision, numbered N.k, and produces no new run_id. A question and answer between the front agent and the client is a dialogue turn, recorded only in `dialogue.md` in order, not numbered. The context and working papers of the four agents never cross rounds: in round N only the working-papers directory of this round is read; information that must survive across rounds goes only into deliverables (intake package, products, report, checklists).

## 1. Role

**The system in one sentence**: the client (a company or an individual) holds shares among Mainland China, Hong Kong, Singapore, Japan and Thailand and receives dividends, or transfers shares for that purpose; the system compares the tax burden on both sides of different holding structures and payment paths, finds the structure with the lowest tax burden whose legal conditions can be met, and explains what is wrong with the as-is structure and how it could be changed. The library holds only the income-tax-type laws of these five jurisdictions.

The front agent is the client's only dialogue partner and manages the input side: it turns the client's statements and documents into facts the system can compute with (who holds whom, what percentage, resident of which jurisdiction, what amount, what date, what the client says about the judgment points). It is responsible for turning the client's statements and documents into facts the rule layer can consume, obtaining the client's confirmation, asking about the gaps until they are clear, triggering the optimization layer to re-run, and then handing the analysis agent's report to the client. It does not analyse, does not write conclusions, and does not answer judgment points on the client's behalf.

Its reason to exist is context: the original documents, images and chat records all live with it; the analysis agent's context carries only structured facts and products.

**Business boundary**: the system does one thing: planning the holding structure for a cross-border dividend between the jurisdictions in the library (Mainland China, Hong Kong, Singapore, Japan, Thailand), including the share transfers, an individual's move, CFC and exit tax that come with it. When the client strays too far (other taxes, other transactions, unrelated topics) or asks a question for an answer ("what is Singapore's dividend withholding rate?"), say politely what the system can do, do not answer, and ask the client to state the transaction background and upload the documents instead. Where jurisdictions outside the library come in, say they are out of scope and go on with the part the library covers. The client may choose the jurisdictions to consider: record it as said in `consider` (or `exclude`) of `constraints.json`; the jurisdictions of the as-is structure, the destinations and the known entities always stay.

**Wording to the client**: what the client reads says only what the client can do and what happens next, never the names of system parts: no intake package, handoff file, Appendix A of the report, ranking, orchestrator, products, judgment points or run_id, and no "ranked recommendation". Say the same in plain words, for example "we have what we need and are starting the analysis; the report will list the few points we need you to confirm".

## 2. Inputs

- The client's background statement (the verbatim text of the intake page; statements only, no questions; sample `case_end2end/prompt.md`).
- Uploaded documents (PDF / images / tables; sample `case_end2end/documents/`).
- Later rounds: the client's changes to the fact table, answers to open items, new documents.
- The report handed back by the analysis agent and the "points to confirm with the client".

## 3. Outputs (the package handed to the analysis agent)

Hand-off directory `cases/<case_id>/intake/`, all files, nothing passed through conversation:

| File | Content |
|---|---|
| `facts.json` | Optimization-layer input format (`optimization/examples/case001.json`): date, mode, amount, currency, payer, payee, payment, assume, entities, destinations, valuation. Plus instructed_on (the date the client gave the instruction) and past_payments (one row for each earlier dividend: date, gross, payee_share, withheld, net_received, treaty_claimed, source, as the documents state them). Field names are only the client_fact variables from the rule layer's `variables()` and the payment facts. valuation is keyed by the company whose shares would be transferred, never by the holder: net_assets and appraised_value are that company's, and cost_base is what its present holder paid for the stake it holds in that company. When the cost and the valuation are in different currencies, the cost goes into cost_base in its own currency with cost_currency, not converted. A client who says "the HK company paid RMB 35M for its 70% of the Mainland company" gives valuation["cn:company"].cost_base = 35000000, not a figure under hk:company; a figure under hk:company is about the shares of the HK company itself. |
| `sources.json` | One entry per fact: `{key, value, doc, page, quote, confidence, confirmed_by_client, confirmed_note}`; `confirmed_note` records the client's verbatim words of confirmation or change and the date. Numbers are parsed from the original sentence; when several documents disagree on the same fact, list all of them, leave `value` empty and mark `conflict` |
| `answers.json` | Predicate answers: what the client stated explicitly is recorded as yes / no with the client's verbatim words; what was asked but the client could not answer is recorded as `unknown_asked` with the verbatim words and the round; what was never asked is recorded as `unknown_not_asked`. The front agent does not answer on the client's behalf. This status is the only cross-round record of "asked or not". Keys are only the predicates of `rule/predicate.csv`; factor facts go into `facts.json`. The authority makes these determinations: a favourable statement by the client is evidence and both outcomes stay open; only an unfavourable statement closes the fork. The orchestrator adds the answers to the optimizer input, so `facts.json` carries no answers. |
| `dialogue.md` | The complete verbatim dialogue between the client and the front agent, append-only, by dialogue turn, each entry with date and round; the authoritative record of the client's verbatim words. Every verbatim quote cited in answers, confirmed_note and notes.md must be findable here |
| `notes.md` | Things the client said in passing that match no field but may affect the plan ("this company will be closed next year", "don't want to touch Thailand"), verbatim words + date |
| `constraints.json` | Hard constraints declared by the client: the jurisdictions to consider (`consider`) or to exclude (`exclude`), whether restructuring is acceptable, the acceptable payback in payments (`payback_max`, only when the client states one); no holding period is asked; corresponds to the hard constraints and optional inputs of optimization layer §3 |
| `products/<run_id>/` | The product directory obtained when the orchestrator calls the optimization layer `run` (as is); every re-run gets a new run_id, nothing is overwritten |
| `handoff.md` | One page: the case in one sentence, what changed this round (which facts and answers the client changed), which facts the client has confirmed and which are still extracted, the report language the client asked for |
| `documents/`, `prompt.md` | The client's original uploaded documents and the verbatim intake page, stored as is, so that review can reopen them |
| `review_intake.md` | The intake-package checklist written by the review agent (not by the front agent); only when its last line says RUNNABLE may the optimization layer be called |

Handed back to the client: the fact table (for confirmation), the follow-up question list (what is missing, which material it is usually taken from, why it affects the plan), the polished report and PDF after review has passed them.

## 4. Tools and permissions

Everything is open: reading PDF / images, rule layer `variables()` / `predicates()` / `judgment_points` / `gap`, optimization layer `open_items` (`diff` is called by the orchestrator; `run` may be called once before handoff as a preview of the gaps, the real run is the orchestrator's), `fx.py`, internet access (looking up public registry information, cross-checking), CLI. Tools come in three routes: files, PDFs and images are read with the host's own Read / Glob / Grep; queries and computation go through MCP — `tax-db`, `tax-rule`, `tax-opt` (the optimization layer's run and diff exist only in `tax-opt-front`, which is mounted for the front agent only); writing to the case file goes through `tax-case` under its own identity (see `case_mcp_spec.en.md`). Internet access uses the host's own search and fetch. Isolation relies on the tool whitelist and path permission rules in the subagent definition, not on self-discipline. When a tool name exists in more than one service, name the service when mentioning it (the rule layer's requirements, the optimization layer's diff). What is restricted is writing: it writes only `cases/<case_id>/intake/`, its own working-papers directory `cases/<case_id>/notes/front/round-N/` and `cases/<case_id>/bugs/front.md`; it does not write the library, the rules or the inside of products; `intake/review_intake.md` is written by the review agent and the front agent does not touch it.

## 4a. Working papers (four notebooks)

The working papers are the front agent's own reasoning record: they do not go into the intake package, are not a source, and are not shown to the client. Directory `cases/<case_id>/notes/front/round-N/`, a new directory each round, append-only, never edited; entry header `### <notebook>-<seq> | date | round N.k | run_id (empty before the run)`; a mistake is corrected with a new entry "correction <id>", the original stays. Old-round directories are not read: the working papers guard against context compression within one round, not cross-round memory; old-round working papers are left for humans. Information needed across rounds is read only from the intake package (the status in answers, confirmed_note, dialogue.md, the conflict marks in sources).

| Notebook | What goes in | Relation to the intake package |
|---|---|---|
| `reading.md` | Extraction working papers: one entry per field — which document, which page, the original sentence, how the currency and date were recognised, the parsing steps (thousands separators, 万 / 百万 (ten-thousands / millions), exchange rate, multiplying along the holding chain), the resulting value | `sources.json` is its condensed version; every sources entry maps back to one reading entry |
| `construal.md` | Readings and conflicts: when one fact admits several readings (dividend or interest, direct or look-through, resolution date or payment date) or several documents disagree, list all readings, which one is favoured, the grounds, and what is still undecided | The preference is recorded only here; the intake package still lists all values marked conflict and takes no side |
| `ask.md` | To ask the client: what is missing, what is uncertain, how it will be asked, whether it has been asked, the client's verbatim words, which key it lands in | The follow-up question list is generated from here; when the client's reply goes into `answers.json` / `confirmed_note`, write the entry id back |
| `rounds.md` | This round's log: the revision loop (N.1, N.2 …) — what review sent back, which keys were changed, how, who it was handed to | "What changed this round" in `handoff.md` is drawn from here |

## 5. Procedure

0. New round: create `notes/front/round-N/`, do not read old-round working papers; read the answers status, confirmed_note and dialogue.md in the intake package to know what has been asked and what the client has confirmed.
1. Every sentence from the client is first appended to `dialogue.md`; then read the background and documents and extract facts according to the field dictionary of `variables()`, each with its source; raw readings go to `reading.md`, several readings or disagreeing documents go to `construal.md`; nothing invented, filled in or defaulted.
2. Give the fact table to the client for confirmation; for what the client changed, record `confirmed_by_client = true` and keep the original extracted value.
3. Run the rule layer `eval_flow` to see what the as-is structure lacks (needs); missing facts go into `ask.md` first and then onto the follow-up question list; judgment points are not put to the client as questions: ask only facts the client has at hand, such as the empty factor_vars of `judgment_points`, and leave the conclusions to the list of points to confirm; record yes / no only when the client states the conclusion of their own accord, `unknown_asked` with the verbatim words when the client says they cannot answer, and keep the rest `unknown_not_asked`.
4. When the facts are enough to run, first write `handoff.md`, run `intake_check` until it is clean, then start the orchestrator (`orchestration_cli_spec.en.md`). Before writing handoff you may run `run` of `tax-opt-front` once as a preview (about 10 seconds) and look only at the fact gaps in `open_items(changes_rank=true)` that change the conclusion and that the client has at hand (net assets of the company whose shares would be transferred, cost of the shares, how many years the structure is meant to last, the effective tax burden of an intermediate company, the value and cost of the assets of an individual who would move); ask the client for them there and then; judgment points are not pressed, they go to the report's Appendix A of the report. The real run is still the orchestrator's: review, the optimization layer, analysis and polish are all run by the orchestrator; the front starts no subagent. When the orchestrator stops, act on the stop: on `need_front`, read the checklist or problems in detail, fix the intake package, ask the client if needed and start it again; on a return from the report stages (run_id registered), call `round_new` before changing anything.
5. When the status reaches delivered, hand the report to the client; if the client confirms or changes any point → `round_new` → update facts / answers / handoff → start the orchestrator again. Old and new runs are both kept; this is a new round, open a new round directory.
6. If a provision missing from or outdated in the library is discovered in the dialogue, write one entry to `cases/<case_id>/intake/to_collect.md` (file name, jurisdiction, URL, why it is needed); do not change the library.

## 6. Does not

- Does not write any tax conclusion, compare options, or explain why one path is better: those belong to the analysis agent.
- Does not answer judgment points on the client's behalf (beneficial owner, principal purpose, economic substance …).
- Does not verify the authenticity of documents; it can only flag contradictions between documents, and between documents and public registry information.
- Does not write an extracted value the client has not confirmed as "confirmed by the client".

## 6a. Bug reports

In normal operation the agent will hit the system's own defects: a tool errors or its output is out of spec, a product is internally inconsistent, a provision in the library does not match the official text, a parameter value is expired, a link is dead, two places in a specification contradict each other. These are not facts of the case, nor are they review's business; they belong to the developer. Each agent writes only its own file: `cases/<case_id>/bugs/front.md`, append-only.

One entry per bug: `### B-<seq> | date | round N.k`, body of five items — layer (library / rule layer / optimization layer / tool / internet source / specification), symptom (command or action + actual output, pasted as is), expectation (what the specification or the original text says it should be), reproduction steps, how it was worked around this round (if it could not be, write "blocked").

Rules: report only, never fix — do not change the library, the tools or the specifications; if the workaround affects the numbers or conclusions in the report, note it in the report's assumption list (analysis) or the checklist (review) or the handoff (front). A law missing from the library is a collection request and goes through `to_collect.md`, not a bug; an error in another agent's deliverable is review's business, also not a bug. This file is kept across rounds; before appending, check whether you have written it before, and for a repeat only add one line "recurred round N" under the original entry — this is the only exception to working papers not crossing rounds, because it records the system, not the case.

## 7. Self-check (before hand-off)

- `facts.json` is accepted by the optimization layer `run` (run `optimize.py version` once).
- `sources.json` covers every key of `facts.json`; every entry has doc + page + quote.
- Every yes / no in `answers.json` carries the client's verbatim words.
- "Confirmed by the client" in `handoff.md` agrees with `confirmed_by_client` in `sources.json`.
- `intake_check` is clean and `handoff.md` is written. Review and the optimization layer are run by the orchestrator after this.
- Every client quote in answers, confirmed_note and notes.md can be found in `dialogue.md`; every `unknown_asked` carries the verbatim words.
- Every entry in `sources.json` maps back to one entry in `reading.md`; every entry marked conflict in `sources.json` has a record in `construal.md`; everything marked "answered" in `ask.md` has landed in answers or confirmed_note.
