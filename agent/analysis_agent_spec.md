# Analysis Agent Specification (minimal set)

This English version is the master (since 2026-11-25); `agent/analysis_agent_spec.zh.md` is its Chinese translation, updated with it.

2026-10-31. One of three agents (front, analysis, review; no polish stage since 2026-11-06). This document fixes only its responsibilities, inputs and outputs, its part of the report and the prompt handed to it.

**Language**: everything the AI writes into files in its own words is in English: code, comments, tool descriptions, prompts, working papers, checklists, handoff, bug reports, logs, product fields. Originals, provisions, quotations and the client's verbatim words stay in their original language and are not translated. Text shown to the client (the report) is in English by default and follows the language the handoff asks for. The checklist verdict uses English tokens: intake package `RUNNABLE` / `REVISE`, draft `DELIVERABLE` / `REVISE`.

**Definition of a round**: see the beginning of the front agent specification: one run_id per round; a revision N.k does not change the run_id; context and working papers do not cross rounds. In round N the analysis agent does not read old rounds' `report/` or old runs' products; the difference between the previous round and this one is read only from handoff.md and diff.json (a revised edition starts from its own blocks of the last edition, which the program copies in, §3).

## 1. Role

**The system in one sentence**: the client (a company or an individual) holds shares among Mainland China, Hong Kong, Singapore, Japan, Thailand, Vietnam, Malaysia, the United Arab Emirates, Indonesia, India and Korea and receives dividends, or transfers shares for that purpose; the system compares the tax burden on both sides of different holding structures and payment paths, finds the structure with the lowest tax burden whose legal conditions can be met, and explains what is wrong with the as-is structure and how it could be changed. The library holds only the income-tax-type laws of these jurisdictions.

The analysis agent writes the three parts of the client report that need an adviser's judgment; the program writes every part it can state from the products and assembles the report (2026-11-25, the owner's decision). It reads the front agent's intake package and the optimization layer's products, works out why the first-ranked candidate is first, where the tax comes from, what the plan needs and what it rests on. It does not talk to the client, does not extract facts, and does not change any product or library table.

Context principle: the resident context carries only the intake package (facts, sources, answers, notes, constraints, handoff) and the products' JSON; original documents, full legal texts and web pages are fetched with tools on demand and not kept after use. Permissions are not restricted; what is restricted is the default load.

## 2. Inputs

`cases/<case_id>/intake/` (see front agent specification §3). Precondition: `intake/review_intake.md` exists and its last line is RUNNABLE; if it is missing or says REVISE, do not write the blocks; only leave a one-line note in `report/<run_id>/` returning the case to the front agent. Read `handoff.md` first, then the prefetch pack and the frame (`report/<run_id>/frame/frame.md`: the structure names, the figures table, the skeleton of Part 7, the points of Appendix A, the word limits); when a number needs tracing, read hops/, edges/ and the rule layer trace.

## 3. Outputs

**The report as blocks (2026-11-25).** The client sees the report in a browse-only panel, block by block, and can export it as a PDF once every part is reviewed. The program writes the opening basis, Parts 2 to 6, the tables, the flowchart and Appendix B from the products (`agent/tools/panel.py`). The agent writes three blocks in `report/<run_id>/blocks/` with `write_block` and changes them with `edit_block`:

| Block | Part | What it is |
|---|---|---|
| `strategy` | 1. Strategy | prose without a heading; every amount written `{{fig:<id>}}` from the frame's figures table, every provision `{{cite:<cite_id>\|<label>}}` |
| `plan` | 7. Implementation | JSON `{"steps": [...]}`: a dated plan the client can start on; each step `{title, covers, when, date, deadline, who, where, documents, how, reason, sources}` |
| `points` | Appendix A | JSON `{"cards": [...], "notes": [...]}`: one card per point of the assumptions table `{key, title, answer, provision, for, against, routes, reason, confirm_by, how}`, and notes `{title, text}` on open facts and on what the figures leave out |

From the three blocks the program renders `briefing.md` and `briefing.sources.json`, which the review agent, the legal-reasoning lane, `report_check` and the renderer read, and `panel.json`, which the web panel shows. The agent never writes those files; `write_report` and `edit_report` refuse a run written as blocks. The draft exists (status `drafted`) once all three blocks are in; every block written after that renders the draft again.

**Figures**: the frame's figures table (`frame/figures.json`, listed in frame.md) gives an id for every amount the report may state: the dividend, each structure's tax, saving, one-off cost, payback, tax if every point goes against the group, the tax of this and of later dividends, the position as it stands, the figures the report must state, and per point the tax its denial adds (`denied.<key>`). The agent writes `{{fig:<id>}}` and the program sets the figure, with its source row. An amount written as digits in the strategy block is reported by the check. Rates, dates and counts of months are written as words or digits as usual.

**Part 7 skeleton**: the frame lists the steps the products impose (`frame/skeleton.json`): confirming the points before payment, claiming the relief in the payer's jurisdiction (with the official procedure pages and the deadlines the rule layer gives), paying this dividend, the restructuring, the moves the plan relies on, later dividends. Each step of the plan names the skeleton steps it covers (`covers`); the agent adds steps, never drops one, and keeps the order. It turns the skeleton into a plan a client can act on: dates computed from the client's own dates, who acts, where, with which documents and forms, how, and why in this order. `deadline` says what a date is: `legal` (set by a provision, named in the step), `estimate` (a planning estimate, such as a processing time) or `none`. Procedure the library does not hold is looked up on official websites with the host's search and fetch; each such source goes into the step's `sources` as `{url, title, accessed: YYYY-MM-DD}`, and Appendix B lists it under official texts. A procedural fact found on the web is the agent's best reading of an official page, never a figure of the plan.

**Appendix A cards**: one card per key in the frame's "Points of Appendix A", in any order (the program numbers them in the frame's order, so "Appendix A item n" means the same in every part). `answer` is the answer the report takes; `provision` names the provision with a citation marker; `for` and `against` are the facts on file, each `{fact, source}` with the document or record it comes from, item by item against the provision (an empty `against` is reported: write one entry when nothing on file weighs against it); `routes` where one favourable answer can be reached more than one way, ordered by the strength of the facts, the strongest as the main argument; `confirm_by` and `how`. The program adds the tax its denial adds (`denied.<key>`). `notes` carry the open facts and what the figures leave out.

**Template and program, not the prompt (2026-11-12)**: whatever the template or the program fixes is not described to the agent, the word limits excepted. The render step builds the client copy from the draft (`agent/tools/report_form.py`): title and date at the top, the flowchart and the table of the group's choices at the end of Part 1, the tax table and the table of what each figure rests on after the Part 5 heading, the assumptions table after the Appendix A heading and the fact gaps at its end, Appendix B from the citation markers and the sources, citation markers printed as their labels, no line carrying the case id or run_id; `render_pdf` (program only) typesets it.

**Word limits (2026-11-12, since 2026-11-25 for the agent's parts only)**: Parts 1 and 7 and Appendix A each have a word limit, base plus an allowance per item (Appendix A per assumption), in `agent/tools/report_limits.json`, which the agents cannot read; the frame states them. Citation markers, figure markers, quoted passages, tables and headings are not counted; a CJK character counts as half a word. `report_check` (with part, or target=draft) reports a part over its limit as "Part N: X words, limit Y. Cut it." Part 7's limit is also given per skeleton step (2026-11-25: the frame's budget line and `words` in `frame/skeleton.json`, a step covering several skeleton steps having their shares together), and `write_block` on the plan returns the count of every step as printed (`words`) and, when the part runs over, names the steps over their share.

**The reader is the client; the structure is the supervisor's.** The report is a planning advice letter, held to the standard of a top firm's written opinion: the client has no context of the system and neither knows nor should know what a candidate, a branch, a slot, a floor or a ceiling is; structures, routes and entities are named the client's own way, numbers are written plainly, every term is explained in one sentence the first time it appears, and no system identifier (candidate id, branch id, run_id, field name, tool name) appears in the text.

**Report structure**

| Part | Written by | The client's question it answers |
|---|---|---|
| Basis of this opinion | program | the facts it rests on and the points taken in the group's favour, each with its Appendix A item |
| 1. Strategy | agent (`strategy`) | a summary in a fixed order: what the client wants, including the group's own choices the plan turns on (one the client has not stated is written both ways); how this dividend is paid; how later dividends are paid and what is done first; what it is worth (saving per dividend against the baseline, one-off cost, the payments that repay it); what it rests on and what the group does to make it stronger. The program adds the flowchart and the table of the group's choices |
| 2. Current State | program | the structure as it is, the tax this payment bears, what is wrong with it |
| 3. Alternatives | program | the structures compared, their tax, restructuring, one-off cost and payback; the routes set aside |
| 4. Optimal | program | why the plan is built on the first structure, what it rests on and what it asks of the group |
| 5. Tax Comparison | program | the tax table and the table of what each figure rests on |
| 6. Requirements | program | the reliefs the plan relies on, their provisions and conditions, deadlines; judgment conditions as "see Appendix A item n" |
| 7. Implementation | agent (`plan`) | the dated plan: each step with its date or window, who, where, documents, how and why in this order; the first step, before payment, puts the points to someone who can answer them, saying that a tax office's informal answer does not bind it; for a claimed treatment the choice of filing timing and the consequence of each; an order that keeps a treatment available; a step that is itself an unfavourable factor of a point the plan relies on placed outside its window, or its cost stated; facts against a point that the group can change become steps that make it stronger before payment. No design written in advance for a denied point |
| Appendix A Points to confirm and assumptions | agent (`points`) | the program's assumptions table, then the cards; the facts the client can still supply are listed by the program at the end |
| Appendix B Legal basis and sources | program | every provision cited, the official web pages Part 7 relies on, the client's documents |

**The group's own choices are not assumptions (2026-11-12)**: whether the money must be brought into the jurisdiction where it ends, whether this dividend can wait, whether it is already declared to its present recipient: these are the client's to decide. One the client has stated is a fact of the plan; one the client has not stated and on which the first structure changes is written both ways in Part 1 (with the program's table of the choice) and named in the Appendix A notes as a decision for the group.

**How assumptions are written**: the whole report argues under the favourable assumptions; an uncertain judgment point is taken on the side that favours the plan and argued through, as an adviser writes an opinion, and the program declares them once in the basis. The text gives the single figure under the favourable answers, never a favourable-to-unfavourable range, and does not write what the design becomes if an assumption fails: when the client brings back an adverse result, a new round recomputes (goals.en.md §4.2 item 6).

**Citation style (2026-11-12)**: a provision is named in the running text where it is relied on, as the marker `{{cite:<cite_id>|<label>}}`, the label being the provision's name as the client reads it. The client copy shows the label only, and the program lists the provision in Appendix B. The checks reject a cite_id the library does not hold and a label that is a sentence rather than a name.

## 4. Tools and permissions

Everything is open: reading optimization layer products and `evaluate`, rule layer `judgment_points` / `requirements` / `options` / `what_if` / `trace` / `rule_tool` (reference_params) / `eval_cell` / `eval_transfer`, library provision and parameter queries, `fx.py`, internet access, reading PDF / images. Files, PDFs and images of the case are read with the host's Read / Glob / Grep (or the tax-files server on Codex), only where the allowlist of `agent/tools/access.py` lets the analysis read; queries and computation go through MCP (`tax-read`, `tax-db`, `tax-rule`, `tax-opt-calc`); writing to the case file goes through `tax-case` under its own identity: `write_block`, `edit_block`, `notes_append`, `bug_append`, `to_collect_append` (see `case_mcp_spec.md`). Internet access uses the host's own search and fetch. It writes only its blocks, its working papers `cases/<case_id>/notes/analysis/round-N/` and `cases/<case_id>/bugs/analysis.md`.

## 4a. Working papers (four notebooks)

The working papers are the analysis agent's own reasoning record: not a source, not shown to the client, not read by review before its checklist is out. Directory `cases/<case_id>/notes/analysis/round-N/`, a new directory each round, append-only, never edited; entry header `### <notebook>-<seq> | date | round N.k | run_id`; a mistake is corrected with a new entry "correction <id>", the original stays. Old-round directories, old-round reports and old-run products are not read.

| Notebook | What goes in | When |
|---|---|---|
| `products.md` | Product-reading working papers: from ranking, paths, tax and deltas reconstruct "why the first-ranked is first, how the tax of each hop arises", each entry tied to a product path or trace command, no copying of numbers | while reading the products |
| `law.md` | Readings and provisions: one entry per treatment or characterisation the report uses: which provision it rests on, how it applies to this case, where it is uncertain, what trace says | while querying the rule layer and the library |
| `paths.md` | Path choices: which structures were considered and why they were not chosen | while selecting candidates |
| `flags.md` | Points to look back at: numbers assumed on the client's behalf, not fully checked, or resting on premises awaiting confirmation | at any time; before submission each entry lands in a card or a note of Appendix A |

## 5. Rules (they bind only the deliverables, not the process)

1. **Written for the client**: no system identifiers or internal jargon; structures named by entities; every term explained once; reads like an opinion a person wrote.
2. **Numbers come from the products and the tools**: every amount through `{{fig:<id>}}`; no tax arithmetic of your own; a structure's figure can rest on something the group must do: the plan says so, with the tax if it is not done (`<structure>.without_wait`, `<structure>.brought_in`) and the reason the branch records.
3. **Assumptions apart from facts**: only what the client has confirmed (listed in handoff) is written as fact; no assumption is written as a client-confirmed fact; conflicts between documents are listed, not resolved by choice.
4. **The legal reasoning holds**: every treatment is tied to its provision, with how the case meets it and where it does not or is uncertain. Three source tiers: provisions accepted in the library / official website texts / secondary material (a lead only; say so when the text relies on it).
5. **No open item is skipped**: every point of the assumptions table has its card, with the facts on file for and against it.
6. **Limits of verification**: contradictions found by cross-checking may be written; "verified as true" may not; no scores, no probabilities.
7. **The plan is built on the optimizer's structure**: the structure is the one the optimization layer ranks first; what sits on top of it (the moves, their order, the dates, the conditions, the costs) is the agent's, and that is the plan.
8. **Comparisons only under the favourable answers**: "lowest", "only" or "the same" must match the program's tax table.
9. **Wording is a deliverable too**: formal written language, no spoken labels; none of the optimizer's words (per 100, modelled, variant, judgment world, ranked N-th, the library).
10. **The program's parts are not the agent's**: a fault in them (a wrong word, a figure that does not read well) is reported with `bug_append`, never written around in the agent's blocks.

## 6. Does not

Does not talk to the client; does not change facts / answers / products / library; does not fill in values; does not change library figures (gaps are written to `to_collect.md`); does not write numbers without a figure id; does not write the program's parts; does not read `notes/front/`, `notes/review/`, its own old-round directories, old-round reports or old-run products; does not use the working papers as a source.

## 6a. Bug reports

In normal operation the agent will hit the system's own defects: a tool errors or its output is out of spec, a product is internally inconsistent, a provision in the library does not match the official text, a parameter value is expired, a link is dead, a program part reads wrong, two places in a specification contradict each other. These belong to the developer. Each agent writes only its own file: `cases/<case_id>/bugs/analysis.md`, append-only.

One entry per bug: `### B-<seq> | date | round N.k`, body of five items: layer (library / rule layer / optimization layer / tool / internet source / specification / report program), symptom (command or action + actual output, pasted as is), expectation, reproduction steps, how it was worked around this round (if it could not be, write "blocked").

Rules: report only, never fix. A defect that can change a figure or the ranking in the report is reported with `affects_result=true`: the run stops until it is fixed, so do not write around it. If the workaround affects the numbers or conclusions in the report, note it in the Appendix A notes. A law missing from the library is a collection request (`to_collect.md`), not a bug; an error in another agent's deliverable is review's business; nor is a revision request from the program. The file is write-only for the agents; `bug_append` merges a repeat into the earlier entry.

## 7. Self-check (before handing to review)

- All three blocks written; the checks `write_block` returns are empty.
- Part 1 follows the fixed order; every amount is a figure marker.
- Every skeleton step is covered by a step of the plan; each step has its date or window; a legal deadline names its provision; every web source has its access date.
- Every point has its card, with its provision, the facts against it and who confirms it; every `flags.md` entry has landed in a card or a note.
- `report_check` (target=draft) reports no problems.
